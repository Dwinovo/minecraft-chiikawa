# 0.1.4 phase 1 implementation plan: errand framework (branch 1.21.1)

> Technical plan for the coder agents, derived from [v0.1.4-design.md](v0.1.4-design.md) (the owner-approved design, in Chinese). Phase 1 = the new framework replaces `IntentSelector`; every existing intent, the idle habits and the 5 social scenes migrate into it with gameplay as close to today as the new interruption rules allow; all GameTests keep passing; the duplicated-state problems of design §2 disappear; contract tests cover every errand. No new gameplay in phase 1.

## 0. Key decisions

- **The executor drives vanilla Brain directly.** No Activities for errands. CORE keeps only `FloatBehavior`, `LookAtTargetSink`, `MoveToTargetSink`. The executor is the only writer of `WALK_TARGET`, `LOOK_TARGET`, `PATH`; the vanilla sinks carry them out in the same tick. The 20 custom Activities, `PetActivities`, `BrainAccessor` (if unused) and every `*JobHandler` are deleted by the end.
- **Migration path.** Data and decision core first (T1). Priority semantics inside today's selector (T2), so the gameplay change is isolated and its GameTest fallout attributable. Runtime core (T3). The switch (T4): all 21 intents become `ErrandType`s; their execution temporarily runs through one scaffolding step, `LegacyActivityStep`, which wraps an old Activity (not an old intent). It is transitional only, enforced by a test, and deleted in T17. Then errands go native one at a time; the first is `pick_up_item`.
- **Errand ids are the old intent ids** (`chiikawa:take_photo` …). The synced `INTENT` string, the `intent.chiikawa.*` translation keys, the `pet_personality` multiplier keys and the debug vocabulary stay.
- **Rests reuse the existing saved memories** (`PHOTO_COOLDOWN`, `GIFT_COOLDOWN`, `SHOP_COOLDOWN`, `TAKE_TASK_COOLDOWN`, `MUSICIAN_RESTING`, `SOCIAL_COOLDOWNS`) as storage; `RestLedger` becomes their only writer. Saves and tests that read them stay intact.
- **Each number lives in exactly one file.** Per-feature numbers stay in `pet_camera`, `pet_gifting`, `pet_interaction`, the music config; errand files point at them by name (`{"from": "chiikawa:camera_retry"}`). Every other number moves into the new `data/<ns>/pet_errand/<errand>.json`.

### 1.2 Types and key signatures

#### 1.2.1 Definition and registry

```java
public interface ErrandType<P extends Plan, T> {
    ResourceLocation id();
    ErrandCategory category();
    Codec<T> tuningCodec();                       // the "tuning" block of the errand's data file
    /** Pure: reads only the view; no random, no writes; same answer when called twice. */
    List<Offer<P>> offers(PetView view, T tuning);
    /** Base score within its priority; default = settings.score(). follow_owner overrides (distance). */
    default float score(P plan, PetView view, ErrandSettings<T> settings) { return settings.score(); }
    /** Pure continue condition at step boundaries; leash/category/capability are checked by the executor. */
    default Check stillWanted(P plan, PetView view, T tuning) { return Check.OK; }
    Routine routine(P plan, ErrandSettings<T> settings);
    default Optional<ResourceLocation> workCounter() { return Optional.empty(); }
    default Set<MemoryModuleType<?>> forgetWhenUnavailable() { return Set.of(); }
    RestStore restStore();                        // where its rests live, 1.2.6
}

public interface Plan {
    Optional<GlobalPos> destination(PetView view); // resolved live: owner, friend and partner move
    default Optional<String> subject() { return Optional.empty(); } // key for per-subject rests
}
public record Offer<P extends Plan>(P plan, int weight) {}  // several offers = variants, picked by weight
```

- `Errands`: `register(ErrandType)`, `get(id)`, `all()`, `generic()`; ids identical to today's `PetIntents` constants. `PetCapability.intents()` is renamed `errands()`.
- `ErrandSettings<T>(int priority, float score, int maxTicks, Rests rests, List<ResourceLocation> yieldsTo, List<ResourceLocation> overlays, Optional<VoiceMoment> startVoice, T tuning)` with a static `of(id)`. An errand with no settings is switched off and logged once (the `CameraSettings` "do nothing rather than guess" rule).

#### 1.2.2 Perception facts (`PetView`)

`PetView` is an interface of read-only queries returning immutable values. `LivePetView` wraps the pet, computes each fact lazily and memoizes it for one evaluation (only what a priority level asks for is computed). Tests use a `TestView` builder (replaces `testing/TestContext.java`).

Methods ported from `IntentContext`: `pos()`, `phase()`, `ownership()`, `personality()`, `anchor()`, `follow()`, `ownerPos()`, `targets()`; `slip()`, `eager()`, `hasArrows()`, `playableSelection()`, `offeringBoard()`, `shopWorthVisiting()`; `socialIdea()`, `engagement()`, `carryingGift()`, `giftPool()`, `examToSit()`, `resultsDesk()`, `whistleHeard()`; `photo()` (a `PhotoOutlook` carrying `List<PhotoPlan> moments` instead of one randomly chosen plan); `idleHabits()`, `nearestVisible(predicate, range)`, `running()`.

The view has no `RandomSource`, no `Brain`, no setters. `PhotoScout.outlook` loses its `PhotoSubjects.choose(..., pet.getRandom())` call: each moment becomes an `Offer` weighted by `camera.subjects()`, and `Decision` draws among them.

#### 1.2.3 Decision (`errand.decide`)

```java
public final class Decision {
    /** Walks priorities from the top down to floorExclusive; stops at the first with an admissible offer. */
    public static Optional<Pick> decide(List<ErrandType<?, ?>> offered, PetView view, Permits permits,
            RestLedger rests, int floorExclusive, RandomSource random, @Nullable DecisionTrace trace);
    /** Pure core: score + noise(randomness), highest wins; then weighted draw among that errand's offers. */
    static Pick pickWithinTier(List<Scored> tier, float randomness, RandomSource random);
}
```

Candidate filter, in order: (1) offered by the pet's capability or generic; (2) `Permits` (`PetConstraints.allows(category)`, owner toggles later); (3) not resting (`RestLedger`); (4) `offers()` not empty; (5) destination within the anchor's **reach**; (6) no errand in its `yields_to` has an admissible offer.

Score = `(score + TASK_BONUS if the slip counts its workCounter + EAGER_BONUS for WORK/FORAGE) × personality.multiplier(id, phase)`, then noise up to `randomness`. Noise only breaks ties among simultaneous candidates. A running errand is never re-scored against its own priority, so equal priorities never interrupt each other. `describe` (debug) runs with `random = null`, so looking changes nothing.

#### 1.2.4 Executor and handle (`errand.run`)

```java
public final class Executor {                      // one per pet, owned by PetMind
    Optional<Running> running();                   // type, plan, settings snapshot, step index, startedAt, priority, tags
    void start(ErrandType<?, ?> type, Offer<?> offer, long now);
    void requestEnd(Outcome outcome);              // applied at the next boundary
    void tick(long now);                           // one tick of the current step
    void deliver(Message message);                 // errand-bound messages go to the running step
}
public interface Step {
    void begin(Handle h);
    StepStatus tick(Handle h);                     // RUNNING | DONE | GAVE_UP(reason)
    default StepStatus onMessage(Handle h, Message m) { return StepStatus.RUNNING; }
    default boolean interruptible() { return true; }  // false only for an action mid-way
    default void release(Handle h) {}              // called on every end: undo world holds
    default PetActivity pose() { return PetActivity.NONE; }  // animation is derived from this
    default String performance() { return ""; }
    default Set<StepTag> tags() { return Set.of(); }   // SEATED, IN_SCENE, PLAYING_MUSIC
}
public sealed interface Outcome { record Done() ...; record GaveUp(String reason) ...; record Interrupted(String cause) ... }
```

`Routine` is an ordered list of step factories plus `Steps.repeatWhile(...)`, built once per start.

`Handle` is the public surface steps get: `walkTo(BlockPos|Entity, speed, closeEnough)`, `stopWalking()`, `blockedTicks()`; `lookAt(Entity|Vec3|BlockPos)`, `clearLook()`; `snapTo(Vec3, yaw)`, `faceYaw`; `action(PetAction)`, `reaction(PetReaction)`, `gesture(name)`, `say(VoiceMoment)`, `tellOwner(Component)`; `startUsingMainHand()`, `stopUsingMainHand()`, `swing()`, `cooldownAttack(ticks)`; `reportWork(counter, n)`, `post(AbstractPet other, Message m)`, `now()`, `self()` (the `PetView`).

`LiveHandle.pet()` is **package-private to `errand.step`**: only library steps reach world APIs that need the entity (`Utils.harvestCrop`, `board.claim(pet)`, `PhotoSystem.request`, music streams). `errand.impl` classes can only compose steps. This is the structural guarantee.

#### 1.2.5 Step and action library (`errand.step`)

- **Movement and waiting, always interruptible:** `WalkTo` (target, speed, close enough, arrive distance, `max_walk_ticks`, `no_way_ticks`; ends `GAVE_UP("unreachable")`), `FollowEntity`, `Wait`, `LookAt`, `HoldStill`.
- **Atomic actions (finish in the tick they begin, never cut):** `PickUp`, `Harvest`, `Plant`, `Collect`, `OpenContainer`, `DepositOne`, `CloseContainer`, `Swing`, `Release` (bow), `Shutter`, `TakePresent`, `HandOver`, `Buy`, `ReserveSlip`, `ClaimSlip`, `SitDown`, `HandIn`, `HearResults`, `Say`, `Gesture`.
- **Special long steps, interruptible:** `Skirmish` (combat footwork, ported from `CombatMoveBehavior`), `DrawBow` (release lowers the bow, never fires), `Aim` (photo), `Write` (exam, tag SEATED), `Read` (results), `Busk` (music stream; release stops it), `PlayPart` (scene part, beats from `PartPlayer`), `Invite` and `AwaitReply`, `WaitForGuest`.
- **Scaffolding, deleted in T17:** `LegacyActivityStep`.

Max-merge for outcomes, replace for reports: a photo stored while the camera is still up writes 12000, and the later `done` (upload wait) must not shorten it; a `failed` report must shorten the wait to the retry. This is today's behaviour that commit 2881d6684 fixed by hand.

#### 1.2.7 Inbox and messages (`errand.inbox`)

- `Inbox`: bounded (32), FIFO with `dueAt` for delayed delivery, `Nudge` coalesces, cleared on remove. The only entry from outside is `PetMind.post(pet, message)`.
- **Two halves (rule).** The inbox is lost with the pet on `remove`, so what a message makes **durable** (saved with the pet or the world: the film roll and photographed biomes, **the rest a ledger report writes** since rests are saved memories, later the wages of `SlipCompleted`) is applied at `post` time, on the server thread (asserted; the photo uploads, payload handlers and ticks already run there, anything else hops with `server.execute`), and only what concerns deciding and the running step (delivery to the step, nudges) waits for the drain. A message with a durable part is a `Message.Durable` (sealed); `PetMind.keep` is its one writer, including its `RestLedger.afterReport`; the inbox then holds it as `Message.Settled(message)`, which `PetMind.settled` handles on the next tick. A new durable message adds one case to each switch.
- `sealed interface Message` records: decision triggers `Nudge(cause)`, `DirectiveChanged`, `CapabilityChanged`, `Hurt(attackerId)`, `Moved(cause)`; whistle `WhistleOrder(order, maxDelay)`, `WhistleHeard(where, from, until)`; results and reports `ExamCalledOff(id, reason)`, `ResultsDue(id)`, `SlipCompleted(PetTask)`, `PhotoResult.Stored(...)` / `PhotoResult.Failed`, `MusicStopped(reason)`; invitation protocol `Invitation`, `InvitationReply`, `SceneStart(treat, eagerTicks)`, `SceneOver`, `Withdrawn`.
- `Cue` (immediate, never queued, never moves the body): `Pose(photographer, lookTicks, gesture, line)`, applied by the recipient's overlay handler. A glance goes through executor gaze arbitration and is skipped if the running step holds the gaze. Immediate so a NoAI friend still poses (`CameraGameTests.a_posed_photo_has_the_friend_say_its_line`).

#### 1.2.8 Invitation protocol between pets

1. The initiator's `socialize` routine: `Invite(partner, scene, side, askPriority = own priority (30), expiresAt = now + reservation_ticks)`, then `AwaitReply` (≤ 5 ticks).
2. The invitee's `InvitationDesk.consider()` accepts only if the constraint filter permits `cooperate` (category SOCIAL, so a sitting pet declines), it is not resting on that subject, and `askPriority > running priority` (or nothing runs). Wandering (10) accepts; working (50) or picking up (30) declines. This is exactly today's `SocialRules.isFree`. On accept it records an `Engagement` and replies; `cooperate` (80) is then the top offer at its next decision.
3. The initiator walks over (`WalkTo` with the approach distance). On arrival it takes the treat out of **its own** bag and posts `SceneStart(treat, eagerTicks)`. The invitee heals, plays the eating sound and calls `feedDish` **on itself**. Both run `PlayPart` for `duration_ticks`.
4. Endings: initiator ends → posts `SceneOver` (done) or `Withdrawn` (gave up / interrupted); invitee ends (interrupted, expired) → its release posts `Withdrawn`. Each side records its own `SOCIAL_COOLDOWNS` rest through its own ledger.
5. `PLAYING_MUSIC` scenes are not invitations: the initiator observes the busker's visible state (perception).

The photo pose is the one-way form: a `Cue`, not an invitation.

## 2. How the executor drives vanilla Brain

- **Brain contents.** Memories and sensors as today. CORE = `FloatBehavior(0)`, `LookAtTargetSink(45,45)(0)`, `MoveToTargetSink(1)`. `AnchorLeashBehavior` leaves CORE in T14. Default activity IDLE with no behaviors. Until T17 the legacy Activities stay registered for the scaffolding step.
- **Tick order** in `AbstractPet.customServerAiStep`: eager upkeep → `mind.tick(level)` → `getBrain().tick(level, this)` → super. The mind writes walk and look targets before the sinks run in the same tick. Sensors run inside `brain.tick`, so the mind sees facts one tick old (same lag as today).
- **`PetMind.tick`:**
  1. Drain due messages: errand-bound ones to `executor.deliver`, the rest to handlers that may set `decideNow` or `executor.requestEnd(...)`.
  2. If an errand runs and its step is `interruptible()`: apply a requested end now; on a decision tick (`(now + id) % 10 == 0`, or `decideNow`) check continuation (capability still offers it, category still permitted, destination within the **leash**, `stillWanted`, `maxTicks` not passed). A failure is `gave_up(reason)` for the errand's own conditions or `interrupted(cause)` for a directive or capability change. Then `Decision.decide(..., floorExclusive = running.priority)` queries only priorities strictly above; a pick interrupts (`interrupted("higher")`) and starts the new errand.
  3. If nothing runs, decide over all priorities every tick (today's `NO_INTENT` trigger).
  4. `executor.tick`: tick the step, advance on DONE; routine end → `done`; GAVE_UP → `gave_up`.
  5. Project derived state: `setIntent`, `setActivity(step.pose())`, `setPerformance`.
- **Every outcome:** `step.release(h)` → erase `WALK_TARGET`, `LOOK_TARGET`, `PATH`, stop navigation → `RestLedger.afterOutcome` → `DecisionLog` → project. An errand with `start_voice` (combat: `hunt`) says it on start unless the previous errand had the same category (keeps `VoiceGameTests.a_pet_setting_off_to_fight_shouts`).
- **"Interrupt only between steps"**: every end is gated on `step.interruptible()`. Movement and waiting are always interruptible; actions complete inside the tick they begin. The bow draw is split into interruptible `DrawBow` and one-tick `Release`, so an archer told to sit does not fire. The longest an interrupt waits is one tick.
- **CORE coexistence:** Float only touches jump control. A lead or riding gives `tethered`: no follow offers, walks time out to `gave_up`. NoAI pets run no mind; only `Cue`s apply to them.
- **Scaffolding (T4–T16):** `LegacyActivityStep.begin` calls `setActiveActivityIfPossible(activity)` plus the old `onStart`. Its `release` runs the old `onStop`, `doStop`s the RUNNING behaviors (`PetActivities.behaviorsOf`), erases walk, look, path, calls `useDefaultActivity()` (today's `switchIntent`, moved verbatim). Always interruptible; ends only through `stillWanted` (the old `canContinue`), outcome `done`, no ledger rest (legacy behaviors still write their own cooldowns until migrated).

## 3. Migration tasks

## 5. Data format

File `data/<ns>/pet_errand/<errand path>.json`; file id = errand id. A `"type"` key is reserved for phase 3's data-only errands.

```json
{
  "priority": 40,
  "score": 0.45,
  "max_ticks": 1200,
  "yields_to": [],
  "overlays": [],
  "start_voice": "hunt",
  "rests": {
    "done":        { "from": "chiikawa:photo_upload_wait" },
    "gave_up":     { "from": "chiikawa:camera_retry" },
    "interrupted": 0,
    "reports": { "stored": { "from": "chiikawa:camera_cooldown" }, "failed": { "from": "chiikawa:camera_retry" } }
  },
  "tuning": { "speed": 0.7, "stand_back": 4, "hold_ticks": 20, "look_back_ticks": 60,
              "view_distance": 16.0, "max_walk_ticks": 400, "no_way_ticks": 100 }
}
```

`start_voice` only on errands that cry out on starting (melee, ranged: `"hunt"`). `RestSpec` is an integer (ticks), `{"ticks": N, "per": "subject"}`, or `{"from": "<source>", "per": "errand|subject"}`.

**Validation at load:** `priority` ≥ 0; `max_ticks` > 0; `gave_up` resolves to > 0; `yields_to` names errands at the same priority; `follow_owner` must not set distances the anchor owns. A failing file disables its errand with an error (the camera rule).

**Existing data (each number in one file):** `pet_camera` keeps `cooldown_ticks`/`retry_ticks` (per camera item), take_photo references them; `pet_gifting` keeps `cooldown_ticks`, gift_owner's `done` is `{"from": "chiikawa:gifting_cooldown"}`; `pet_anchor` keeps reach, leash, teleport and follow start/arrive (follow_owner reads them); `pet_interaction` keeps reservation, duration, cooldown, chance, approach per scene (socialize/cooperate rests `{"from": "chiikawa:scene_cooldown", "per": "subject"}`, `max_ticks` only an upper bound); music config keeps `retry_seconds`, `max_track_seconds`; `pet_personality` keeps `intent_multipliers` and `routine` keyed by the same ids. Every hard-coded behaviour constant today (`GIVE_UP`/`MAX_*` ticks, `REST_TICKS`, speeds, distances) moves into the errand file.

## 6. Risks

1. **Save compatibility.** `PHOTO_COOLDOWN`, `GIFT_COOLDOWN`, `PHOTOGRAPHED_BIOMES`, the five farmer `*_POS`, `HOME` keep ids, codecs and meaning. Removed memories were never saved. Executor state is not saved (as `CURRENT_INTENT` was not). On load, a pet with a pending gift (saved NBT `Gift`) is offered gift_owner at once; board reservations expire by time.
2. **Synced `INTENT` string**: same ids; client UI, translations, debug keep working; now a projection written only by the executor.
3. **Ports to the 14 other branches.** Finish phase 1 on 1.21.1 before porting. Keep version-sensitive calls in `LiveHandle`, `LivePetView`, the step library, `ErrandSettingsLoader` (copy each branch's own `CameraSettingsLoader` shape; `SimpleJsonResourceReloadListener` changed in 1.21.2). Build ids through one `Errands.id(path)`. Deleting Activities and `BrainAccessor` reduces the mixin surface. Contract GameTests use `@GameTestGenerator` (absent in the 1.21.5+ data-driven framework): keep scenario logic in plain static methods so each branch only rewrites the registration shim. Port one branch per agent session from a checklist of the T1–T17 files.
4. **Performance**: better than today (a working pet only queries priorities above 50 on decision ticks; lazy memoized facts; the debug command no longer rolls photo dice). Watch `GiftPool.of` (backpack scan) at 80 every 10 ticks; memoize per tick if it shows in Spark.
5. **One-tick message latency** (invitation round trip ~2 ticks, results 1 tick): GameTests use `succeedWhen`/`thenWaitUntil`; none assert same-tick effects.
6. **Behaviour drift from the priority rules**: same-priority work is no longer cut mid-errand; cooperate and the exam now resist work. Deliberate, isolated to T2, listed in the priority table.
7. **Stale entity references** in plans and messages: every step checks `isAlive()`/`isRemoved()` and gives up; the inbox is cleared on remove.
8. **Data-pack reload mid-errand**: `Running` keeps the `ErrandSettings` snapshot it started with.

## 9. Step 2: work as data (gameplay unchanged)

Design §4.2, §12 step 2. Each kind of work (harvest, plant, deliver, weed, pick_mushroom, melee, ranged, play_music) becomes one data file that names a generic **action** written in code; each job declares its work list in data. Gameplay identical: every existing GameTest and JUnit assertion stays as it is.

### 9.1 Decisions

- **D1. Work data lives in the errand's own `pet_errand/<id>.json`.** A file with an `"action"` key is a work errand; a file without one is a code errand. One file per errand, so priority, rests and tuning are never in two files.
- **D2. Old saves.** The five saved `*_POS` memory ids are replaced by one saved `WORK_SIGHTS`. Before anything is removed, W2 proves whether vanilla's `Brain` codec drops *all* memories of a pet whose save holds an unregistered memory id. If it does, the old ids stay registered (codec kept) but leave `AbstractPet.MEMORY_TYPES`, and the rule "an id a save may hold stays registered" is written in one place; if vanilla keeps the rest (partial result), the old ids are deleted (W12).
- **D3. Gifts never including work items is a gameplay change** (design §7.3, the "always seeds" report). It is the first task of step 3, not step 2. No unused work-item API is added in step 2.
- **D4. Tools and materials are not work-file fields.** The tool is the job's tag (code, clients need it); materials belong to the action, because the vanilla call decides them (seeds: `CropHandler.isSeed`; arrows: `ARROW_ONLY`). `WorkItems.of(job)` = tool tag plus the job's actions' `materials()`, added in step 3 with its first reader. No `output` field (the bag is the only output; the container of `deliver` is its target).
- **D5. Fight files name no counter.** `slay` is reported by the death hook; naming it would give fights the slip bonus at priority 80. `pet_task.capability` keeps naming the job.
- **D6. A job's work list is data:** `data/<ns>/pet_job/<job>.json` = `{"work": [ordered errand ids], "sight": {...}}`, order kept exactly (tie-break and noise order). The job registry (numeric `PetJob` id, tool tag, Hachiware rule) stays code; `PetCapability.errands()` goes.
- **D7. `WORK_SIGHTS` is not saved** (`Map<ResourceLocation, List<BlockPos>>`, nearest first, first = chosen). It replaces the five `*_POS` and `FARM_SIGHTS`. W2 showed that an unknown memory id in a save wipes every memory of the pet, so each new saved id is one more id that must stay registered forever and one more way a downgrade loses memories. A farmer loaded mid-field finds its blocks again at the sensor's next scan (at most 20 ticks). The five `*_POS` stay registered with their codecs, leave `MEMORY_TYPES`, and are never read again (an unlisted memory throws on `getMemory`); the rule "an id a save may hold stays registered" is written once, where they are registered.
- **D8. The work sensor's numbers are data** (data over hardcode): the job file's `"sight"` block holds radius (5), vertical range (1), forget distance (10), backoff step (30) and empty-streak limit (3), read by the one work sensor. Today's constants, moved, not changed.

### 9.2 Model

- **Actions** (`entity/brain/errand/work/action/`, a fixed registry `WorkActions` like `Overlays`): `harvest_block` (`WalkTo`, `Harvest` absorbing `Collect`, tuning `tool_wear`: harvest 1, weed and mushroom 0), `plant_block`, `deposit` (`OpenContainer`, repeat `DepositOne`, `CloseContainer`, `Lid` release), `strike` (`Skirmish`, `Swing`, `Stance`), `shoot` (`Skirmish`, `DrawBow`, `Release`), `busk` (`Busk`, registers `music_retry`). Each owns its tuning codec, rest store kind, rest sources, plan record, `offers`, `stillWanted`, `routine`, `forgetWhenUnavailable`, `materials()`.
- **`WorkErrand`** (one class) implements `ErrandType` from a `Work(action, category, counter, requires, target)`; requirements (`wild_or_slip` needs a counter, `at_night`) first, then the action.
- **Targets** (`WorkTarget`, sealed, dispatch on `"type"`, each with its `missing` reason key so the `intent.chiikawa.fail.*` keys stay): `ripe_crop`, `plantable_soil`, `blocks` (block tag; a `HALF` block only at its lower half), `container` (block tag and item tag), `foe`. Tags via `TagKey.hashedCodec`.
- **Registry and ids.** `Errands` = the 13 code errands plus the loaded work errands, installed together with `ErrandSettings` by the loader (and by `TestErrands.load`, through the real loader). Ids unchanged, so the synced `INTENT`, translations, personality keys, rest keys and contract scenarios stay. Work ids leave `ErrandIds` for `data/WorkData` (datagen and tests only). Counters are data ids owned by the work files; `PetWorkCounters` keeps only `SLAY`.
- **Sensors.** `PetWorkSensor` replaces `PetFarmerWorkSensor`: one spiral for all block works of the pet's job, gated by "the job has block works", writing `WORK_SIGHTS` (sole writer). The attack sensor's gate becomes "the job has a `foe` work". `JobWork.errandsOf(pet)` is the one function `PetMind.offered`, both sensors and `PerceivedTargets.capture` use.
- **Reload.** `Running` keeps its `ErrandType`; continuation and offered checks compare ids; a vanished errand ends without a rest-store error. Cross-file checks list the pack's `pet_errand` ids from the `ResourceManager`, never another loader's state.
