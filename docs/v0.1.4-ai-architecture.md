# 0.1.4 技术设计：差事框架

> 本文按现在的代码写，描述 0.1.4 已经做完的宠物 AI 框架，不是计划。
> 它取代 [v0.1.0-ai-architecture.md](v0.1.0-ai-architecture.md) 里关于意图和 Activity 切换的部分，也就是 4.5 到 4.10 和第 5 章。归属、约束与锚点、许可表、能力、性格、传感器、工作牌、商店这些部分没有变，仍以那份文档为准。
> 设计依据见 [v0.1.4-design.md](v0.1.4-design.md)，迁移的经过和各分支的移植清单见 [v0.1.4-implementation.md](v0.1.4-implementation.md)。
> 基于 1.21.1 分支。

## 1. 总体模型

0.1.0 的"意图"现在叫"差事"（errand）。名字换了，是因为内容也换了：差事不再对应一个 Activity，不再靠分差抢位置，它有写在数据里的优先级，由一个执行器一步一步做完。

| 0.1.0 | 0.1.4 |
| --- | --- |
| 意图 `PetIntent`，无状态，分数写在代码里 | 差事 `ErrandType`，无状态，优先级、分数、冷却都在数据里 |
| `IntentSelector` 每次评估都重新打分，用容差防抖 | `PetMind` 决定，`Executor` 执行。优先级严格分层，同级不打断 |
| 一个意图对应一个 Activity，逻辑在 Behavior 里 | 差事是一串步骤，执行器直接驱动 Brain。Activity 只剩 CORE 和空的 IDLE |
| 六处记忆各自记冷却，各行为自己写 | 一本歇息账 `RestLedger` |
| 外部系统直接改宠物的记忆和字段 | 一律发消息到宠物的收件箱 |
| 宠物之间靠一块预约记忆 | 邀请协议，各管各的状态 |

没有变的四层：

- 归属（`PetOwnership`）：野生还是有主人。
- 约束（`PetDirective` 经 `PetConstraints`）：得出锚点和许可表，差事只能看到这两样，看不到指令本身。
- 能力（`PetCapability`）：由主手工具得出，`errands()` 列出它额外提供的差事。
- 性格（`Personality`）：给每个差事一个分数倍率，再加一点随机。

```
 归属 ─┐
 约束 PetDirective ─▶ PetConstraints ─▶ 锚点 + 许可表 ─┐
 能力 PetCapability ──────────────────▶ 提供的差事 ────┤
 性格 Personality ─┐                                   ▼
 传感器写入的记忆 ─┴─▶ PetView ─────────────▶ Decision（PetMind 调用）
                                                       │ 选出差事和计划
 收件箱 Inbox ◀── 外部系统、别的宠物                    ▼
        │                                         Executor ─▶ 步骤 ─▶ Handle ─▶ 宠物
        └──▶ PetMind 读取并处理                         │
                                                        └─▶ 结束时写 RestLedger、DecisionLog
```

### 1.1 每个 tick 的顺序

```
AbstractPet.customServerAiStep
  兴奋状态到期处理
  PetExams.upkeep(this)          考试的通知发进收件箱
  mind.tick(level)               读收件箱，决定，执行器走一步
  getBrain().tick(level, this)   CORE 里的移动和看向把本 tick 设好的目标执行掉
  super.customServerAiStep()
```

`PetMind` 在 Brain 之前运行，所以它设的走和看会在同一个 tick 被执行。传感器在 `brain.tick` 里运行，所以 `PetMind` 看到的事实比世界晚一个 tick。

### 1.2 Brain 里还剩什么

`AbstractPet.makeBrain` 只做三件事：

- CORE 活动里放 `FloatBehavior`、`LookAtTargetSink(45, 45)`、`MoveToTargetSink`。
- 默认活动是原版的 `IDLE`，里面没有任何行为。
- 最后调用 `useDefaultActivity()`。新建的 Brain 一个活动也没有，包括 CORE，不调用这一句宠物会站着不动。

记忆和传感器照旧在 Brain 里。mod 不再注册任何 Activity，也就没有 `BrainAccessor` 这个 mixin。

## 3. 一次决定怎么做出

### 3.1 什么时候决定

`PetMind.tick` 里，满足下面任一条就决定一次：

- 宠物没有在做任何差事，每个 tick 都决定。
- 到了决定的时刻，`(gameTime + entityId) % DECISION_INTERVAL == 0`，间隔是 10 tick，按实体号错开。
- 刚被告知了可能改变主意的事，也就是 `decideNow` 被置位：指令改变、能力改变、被打、被传送、给了钱或东西、听到哨声、邀请被接受、工作牌完成、考试通知。

决定的前提是当前步骤此刻允许被打断（见 4.4）。一个差事正常做完（`done`）的同一个 tick 会马上接着决定一次，所以一只宠物从一个短差事换到下一个，不会有一个 tick 是"什么都没做"。

### 3.2 候选怎么过滤

候选是通用差事加上当前能力提供的差事。每个候选依次过 `Admission`：

1. 许可表允许它的类别（`Permits`，背后是 `PetConstraints.allows`）。
2. 它整体不在歇息中。
3. `offers(view, tuning)` 有东西可给。
4. 没有被歇息挡住的方案。方案可以带一个"对象"（`Plan.subject()`），对这个对象在歇息就不算。
5. 方案的目的地在锚点的 `reach` 之内。

第 5 条是"宠物能去多远"唯一被问的地方，没有哪个差事自己检查区域。

### 3.3 优先级分层

通过过滤的差事按优先级分层，从最高的一层往下看，遇到第一个有可开始差事的层就停：

- 优先级高的层只要有一个差事能开始，低层的差事不管分数多高都不会被看。
- 正在做差事时，只看严格高于它的优先级（`floorExclusive`）。同级的差事永远不会打断正在做的差事。
- 没有在做差事时，从最高层往下看。

### 3.4 层内怎么选

同一层里的差事比分数：

```
分数 = (差事的 score
        + 0.2     如果身上的工作牌计这个差事的工作（TASK_BONUS）
        + 0.15    如果宠物处在兴奋状态且这是 WORK 或 FORAGE 类（EAGER_BONUS）)
       × 性格倍率（按差事 id 和一天中的时段）
```

再给每个候选加一个不超过性格 `randomness` 的随机扰动，取最高的。所以随机性只在同一层里分数相近的差事之间起作用，不会让宠物放下重要的事去做别的。只有一个候选、或 `randomness` 为 0 时不抽随机数。

选出差事后，如果它有多个方案（`Offer`），按权重抽一个。方案是同一差事的几种做法，比如闲逛有看玩家、看生物、散步、发呆几种，拍照有几个想拍的时刻。

`Decision` 是纯函数，不认识宠物、Brain 和世界，只吃传进去的东西，所以可以用固定种子的随机数测试。

### 3.5 yields_to

数据里 `yields_to` 列出同优先级的另一些差事，意思是它们能开始时，这个差事不开始。农夫的严格顺序就这样表达：收割优先于种植优先于送货。这不靠分差，因为性格倍率会抹平分差。

这个顺序要成立，农夫就得一直知道整片地，而不是只记得一块。`PetFarmerWorkSensor` 每次扫描把每种方块在范围内找到的全部都记下来，由近到远，第一块放在原来那种记忆里，其余的放在不存档的 `FARM_SIGHTS` 里，只有传感器写它们。传感器每次运行都会去掉已经不成立、太远或正在歇着的方块，视图给出的是记着的方块里第一块仍然成立且没在歇的。所以刚收完一棵作物，下一棵在同一个 tick 就已经知道，只要还知道有熟了的作物，送货就一直让位，不会在两次扫描之间的空档里跑去送货。

两点要记住：

- 只在开始时看。种植进行中，收割变得可以做了，种植不会被打断。
- 只看对方此刻能不能开始，不管对方自己又让给了谁。

### 3.6 继续还是结束

正在做的差事，在决定的时刻由 `Continuation.endOf` 依次问：

1. 当前能力还提供它吗。否则结束为 `interrupted("capability")`。
2. 指令的许可表还允许它的类别吗。否则 `interrupted("directive")`。
3. 差事自己的 `stillWanted` 通过吗。否则 `gave_up(原因)`。
4. 还在拴绳之内吗，见 3.7。否则 `gave_up("out_of_leash")` 或 `gave_up("left_area")`。

之后才去问有没有更高优先级的差事可以开始。有，就先把当前的结束为 `interrupted("higher")`，再开始新的。

### 3.7 拴绳规则

锚点有两个半径，`reach` 管开始，`leash` 管继续。`reach` 小于 `leash`，中间的差值是追击余量，宠物不会在"追出去、被拉回、再追"之间来回。

- 有目的地的差事（`Plan.destination` 有值）：开始时目的地要在 `reach` 内，继续时目的地要在 `leash` 内。目的地是现算的，主人、朋友、搭档会动。
- 没有目的地的差事（演奏、坐着写卷子、原地发呆）：继续时看宠物自己是否在 `leash` 内，出了就 `gave_up("left_area")`。
- 回去的路由闲逛差事的 `Returning` 变体负责。宠物在 `leash` 之外时，闲逛只提供这一个变体，目的地是活动区域的中心。
- 被牵着或骑乘的宠物没有拴绳。跟随主人时锚点中心是主人，宠物落得太远由 `PetFollowKeeper` 传送，不由差事处理。

### 3.9 看一只宠物为什么这样选

`/chiikawa debug intent` 看宠物当前的差事、每个差事这一刻的情况（为什么不能开始，或者优先级和分数），`log` 看最近的开始和结束。这里的决定用 `random = null` 调用 `Decision.decide`，只看不抽，不会改变宠物的随机数序列。

`DecisionLog` 记最近 20 条，每条是一次切换（从哪个到哪个、为什么、这一层的排名）或一次结束（哪个差事、什么结果、跑了多久），只在内存里。

## 4. 差事的一生

```
offers（纯）─▶ 过滤、分层、选出 ─▶ Executor.start(计划, 一串步骤)
                                          │
                       每个 tick：begin ─▶ tick ─▶ DONE ─▶ 下一步
                                          │
                  结果 ◀── 做完 / 放弃 / 被打断（只在步骤之间）
```

### 4.1 差事、计划、方案

`ErrandType<P, T>` 是无状态的定义，`P` 是计划的形状，`T` 是调参的形状。它要实现：

- `offers(view, tuning)`：现在宠物有哪些做法。答案是 `Offers`，要么至少一个 `Offer`（计划加权重），要么一个失败的 `Check` 说明为什么没有。开始条件和调试命令显示的原因是同一个答案，不会分叉。
- `routine(plan, settings)`：这个计划的一串步骤，每次开始新做一份。
- `stillWanted(plan, view, tuning)`：继续条件，可以比开始条件宽松。
- `category()`：类别，许可表按它放行。
- `restStore()`：歇息记在哪里，见第 6 节。
- 可选的有 `score`（分数随情况变，比如跟随随距离变）、`workCounter`、`forgetWhenUnavailable`、`problem`（只有这个差事自己知道的数据检查）、`restSources`。

`offers` 和 `stillWanted` 必须是纯的：只读 `PetView`，不抽随机数，不写任何东西，问两次答案一样。这是被问到"现在行不行"的那一刻的约束，因为调试命令、契约测试和 `Decision` 都会问。

`Plan` 是宠物决定去做的这一件事，比如这一块作物、这一张照片、去那块公告板。它有三个可选的问题：

- `destination(view)`，目的地，现算。
- `subject()`，歇息按对象记时用的键，比如够不着的那块作物、一起玩的那只宠物。
- `restKey()`，歇息时长依赖的相机或场景。

### 4.2 路线与步骤

`Routine` 是一串"部分"（`Part`），每一部分按顺序给出自己的步骤，轮到时才造这一步，所以步骤看到的是那时的世界，不是出发时的世界。有三种写法：

- `Routine.step(supplier)`，一步。
- `Routine.repeatWhile(条件, 步骤...)`，条件成立时一轮一轮地做，每轮开始前和两轮之间问条件。收割的送货就是"只要还放得下就一个一个放"。
- `.releasing(consumer)`，整个差事结束时放手一次。用于跨步骤持有的东西，比如礼物从拿出来到交出去一直在爪子里，不管在哪一步结束都要放回去。

`Step` 的接口：

- `begin(handle)` 开始，`tick(handle)` 每 tick 一次，返回 `RUNNING`、`DONE` 或 `GAVE_UP(原因)`。
- `onMessage` 收到和当前差事有关的消息，比如音乐放完了。
- `release(handle)` 结束时放手，不管是做完、放弃还是被打断，只调用一次。
- `pose()` 和 `performance()` 是这一步宠物摆什么姿势、演什么场景，动画由此得出。
- `tags()` 是别的系统会问的状态：`SEATED`（坐在考桌前）、`IN_SCENE`（在演场景）、`PLAYING_MUSIC`。
- `holdsGaze()` 这一步每 tick 都重设视线，别人的一瞥不用插进来。

### 4.3 结果

每个差事结束一次，也只结束一次，结果是三种之一：

| 结果 | 意思 |
| --- | --- |
| `done` | 做成了 |
| `gave_up(原因)` | 做不成，或者超时。原因是短键，比如 `timeout`、`unreachable`、`no_room` |
| `interrupted(原因)` | 被别的事拿走了，比如 `higher`、`directive`、`capability`、`moved` |

结束时按固定的顺序来：先让当前步骤放手，再让路线放手，然后清掉走、看和路径，写歇息，记日志，最后清掉告诉玩家的"在做什么"。

超过数据里的 `max_ticks` 也算放弃，原因是 `timeout`。

### 4.4 打断只发生在步骤之间

结束差事的请求（`requestEnd`）、超时、更高优先级的差事，都要等当前步骤允许才生效。`Step.interruptible()` 默认为真，只有做到一半不能停的动作才该返回假。现在的步骤都可以被打断：移动和等待随时可停，原子动作（拾取、收割、开箱、交礼物等）在自己的那一个 tick 里做完，所以请求在动作之前到就干净地赢，在动作之后到就在下一个 tick 生效。一个请求最多等一个 tick。

拉弓就是这样做的。拉弓（`DrawBow`）可以被打断，打断只是放下弓，不会射出去；松手（`Release`）是单独的一步，只在拉满之后射。所以一个正在拉弓的弓手被叫去坐下，不会放箭。

### 4.5 执行器和句柄

`Executor` 是每只宠物一个，唯一能动宠物的走、看、路径，也是唯一决定告诉玩家"在做什么"的东西。

步骤对宠物做的一切都通过 `Handle`：走到哪里（`walkTo`）、停下（`stopWalking`）、看哪里（`lookAt`、`clearLook`）、做动作和表情、说话、告诉主人、用主手、挥一下、攻击冷却、汇报工作（`reportWork`）、汇报歇息（`report`）、给别的宠物发消息（`post`）或发 Cue（`cue`），加上 `now()`。

`LiveHandle` 是真正对着宠物的实现。它的 `pet()` 只对 `errand.step` 包可见，所以只有步骤库里的步骤才能碰到需要实体的世界接口，比如收割、开箱、请求拍照。`errand.impl` 里的差事只能组合步骤，碰不到宠物。这个约束由 `StateOwnershipTest` 检查（见第 9 节）。

`stopWalking` 除了清掉三个记忆，还会让 Brain 里正在跑的 `MoveToTargetSink` 立刻放手，并停下导航。原因是原版的移动行为在运行期间会记着上一段路径，如果新目的地离旧的不超过两格，它不会重新规划，会继续沿旧路径走。结果是一只刚从散步转去收一块够不着的作物的宠物，要把散步的路走完才被告知"没有路"。

### 4.6 走不通怎么办

`MoveToTargetSink` 在规划路径时，如果没有路，或者只有一段到不了目标的部分路径，会设置 `CANT_REACH_WALK_TARGET_SINCE`，然后照样沿部分路径走。`Handle.blockedTicks()` 读的就是这个记忆。

`WalkTo` 有两种用法：

- 普通的 `WalkTo(..., noWayTicks)`：要站到某处去做事（作物、物品、箱子、相机的位置）。移动行为说"没有完整路径"超过 `no_way_ticks` 个 tick 就放弃，0 表示第一次就放弃。
- `WalkTo.near`：只要走近就行（公告板、考桌）。部分路径是"能走到的最近处"，一直走到头，只有移动行为放掉了走的目标、而宠物还没到够近时才放弃。

宠物离开地面的 tick 里，移动行为规划不了路径，这时它的说法不算数，由 `Handle.canFindWay()` 判断，与原版的 `GroundPathNavigation.canUpdatePath` 一致。

### 4.7 叠加层

`Overlay` 是差事进行时顺便做的小事，比如闲逛时偶尔说话。它不是步骤：不属于路线，不会结束差事，只能说话和瞥一眼（`Aside`），不能让宠物移动。执行器在差事进行的每个 tick 调用一次。

叠加层的 id 固定在 `Overlays` 里，数据里的 `overlays` 引用它们，写了不存在的 id，这个差事的数据加载失败，差事被关掉。现有一个：`chiikawa:idle_chatter`，挂在 `wander` 上。

### 4.8 投影

玩家的游戏看到宠物在做什么，来自三个同步字段，只有执行器写它们：

- `INTENT`：当前差事的 id（字段名沿用，值就是差事 id）。
- `ACTIVITY`：姿态，来自当前步骤的 `pose()`。
- `PERFORMANCE`：场景动画，来自当前步骤的 `performance()`。

姿态和场景只在步骤声明的内容变了时才发布，步骤结束的那个 tick 清掉。动画因此是逻辑的结果，不再是逻辑的来源。

## 5. 步骤库

所有步骤在 `errand.step`，按用途分：

| 用途 | 步骤 |
| --- | --- |
| 走和跟 | `WalkTo`、`WalkTo.near`、`FollowEntity`、`Amble`（散步和回家）、`Approach`（走向要玩场景的搭档） |
| 等和看 | `LookAt`、`Glance`、`Pause`、`Hold` |
| 作物与物品 | `PickUp`、`Harvest`、`Plant`、`Collect`、`OpenContainer`、`DepositOne`、`CloseContainer` |
| 钱与礼物 | `Buy`、`TakePresent`、`HandOver` |
| 工作牌 | `ReserveSlip`、`ClaimSlip` |
| 考试 | `SitDown`、`Write`、`HandIn`、`Read`、`HearResults` |
| 战斗 | `Skirmish`、`Swing`、`DrawBow`、`Release`，`Stance` 是它们共用的站位 |
| 拍照 | `Aim`、`Shutter`、`Hold` |
| 音乐 | `Busk` |
| 场景 | `Invite`、`AwaitReply`、`StartScene`、`WaitForGuest`、`PlayPart`，`Meeting` 是两边共用的状态 |

`Goal` 是步骤要去的或看的东西：一个地点（`Place`）、一个生物（`Creature`，按 id 存，每次重新找）、主人（`Owner`）、考桌的椅子（`Chair`）、容器（`Container`）、吹哨的人（`Whistler`）、一片视野（`Horizon`）。按 id 存而不是存实体，是因为目标可能已经离开世界，计划不能抓着它。

写新步骤的规矩：

- 一步只做一件事，原子动作在自己的 tick 里做完。
- 持有的东西在 `release` 里放手：开着的箱子、爪里的礼物、拉着的弓。
- 目标没了就 `gave_up("gone")`，不要抛异常。
- 凡是有版本差异的世界接口，只放在 `LiveHandle`、`LivePetView` 和步骤里，差事类里不出现。

## 6. 歇息

差事结束后要隔一段时间才会再被考虑，这段时间叫歇息。所有歇息只有一本账：`RestLedger`，写歇息的只有它（通过 `RestStore`）。

### 6.1 存在哪里

歇息的时长怎么存、存在哪里是 `RestStore.Kind`，每个差事通过 `restStore()` 声明：

| 存储 | 差事 | 存档 |
| --- | --- | --- |
| `PHOTO_COOLDOWN` | `take_photo` | 存 |
| `GIFT_COOLDOWN` | `gift_owner` | 存 |
| `SHOP_COOLDOWN` | `shop` | 不存 |
| `TAKE_TASK_COOLDOWN` | `take_task` | 不存 |
| `MUSICIAN_RESTING` | `play_music` | 不存 |
| `SOCIAL_COOLDOWNS`，按场景加搭档的键 | `socialize`、`cooperate` | 不存 |
| `SUBJECT_RESTS`，按对象 | 农活（`harvest`、`plant`、`deliver`、`weed`、`pick_mushroom`）、`pick_up_item` | 不存 |
| `ERRAND_RESTS` | 其余全部 | 存 |

前几项沿用 0.1.3 就有的记忆，所以 0.1.3 的存档里正在走的相机和礼物冷却读进来还在。

### 6.2 结果与汇报

写歇息有两种方式，因为发生的是两种事：

- 结果（`afterOutcome`）：差事结束时由执行器写，按数据里 `done`、`gave_up`、`interrupted` 三项之一。取最大值合并，只会延长，不会缩短已有的歇息。
- 汇报（`afterReport`）：步骤做了某件事、或等的东西回来了，按数据里 `reports` 里的名字写。替换，可以缩短。

必须分开，拍照就是例子。快门按下后，步骤汇报 `taken`，歇息等上传的时间。照片存下来时汇报 `stored`，相机冷却变成 12000。随后差事以 `done` 结束，它不能把 12000 缩回等上传的时间，所以结果取最大值。照片没回来时汇报 `failed`，要把等上传缩短成重试的间隔，所以汇报替换。

场景也是这样。开始演（`played`）是一次汇报，整个冷却从那时算起，之后不管怎么结束，结果都不会缩短它。

`gave_up` 的歇息必须大于 0，否则差事会在同一口气里被再次选中。数据加载时校验。

### 6.3 时长从哪里来

歇息的值（`RestSpec`）可以是：

- 一个整数，差事整体歇这么多 tick。
- `{"ticks": 40, "per": "subject"}`，只对这个对象歇。
- `{"from": "chiikawa:camera_retry"}`，引用别处的数字，`per` 同样可选。

被引用的数字不重复写，来源由差事注册（`ErrandType.restSources()`）：

| 来源 | 来自 |
| --- | --- |
| `camera_cooldown`、`camera_retry` | `pet_camera`，按相机物品 |
| `photo_upload_wait` | 照片上传的等待 |
| `gifting_cooldown` | `pet_gifting` |
| `music_retry` | 音乐配置 |
| `scene_cooldown` | `pet_interaction`，按场景 |

数据里引用了没人注册的来源，数据加载就失败。运行时如果来源丢了，歇息为 0 并记一次错误日志。

### 6.4 汇报必须是持久的

收件箱会随宠物离开世界而丢掉，而歇息是存档的，所以由一条消息引起的歇息，在发消息的那一刻就写，见 7.3。

## 7. 收件箱

外部系统不碰宠物的内部状态，只把一件事告诉它。唯一的入口是 `PetMind.post(pet, message)`，客户端调用不做任何事。

### 7.1 收件箱

`Inbox` 最多 32 条，先到先处理，每条可以带"到期时间"，没到期不读。`Nudge` 合并，同一时间只留一条，取更早的到期时间。满了丢最旧的，因为最新的最可能还成立。宠物离开世界时收件箱清空。

宠物的 AI 关闭（`NoAI`）时不跑 `PetMind.tick`，消息留在收件箱里，只有 Cue 还能生效。

### 7.2 消息

| 类别 | 消息 | 效果 |
| --- | --- | --- |
| 触发决定 | `Nudge`、`DirectiveChanged`、`CapabilityChanged`、`Hurt` | 下一个 tick 立刻决定 |
| 被带走 | `Moved(原因)` | 停下走、看，当前差事结束为 `interrupted("moved")`，再决定。传送、召回、跟不上主人的传送都发它 |
| 哨声 | `WhistleOrder(指令, 最长等待)`、`WhistleHeard(位置, 开始, 结束)` | 有主人的宠物等一段自己随机的时间再照做；野生宠物记下哨声，`answer_whistle` 才被提供 |
| 考试 | `ExamCalledOff`、`ResultsDue` | 取消考试、出成绩 |
| 工作牌 | `SlipCompleted` | 发工资、记录、再决定 |
| 拍照 | `PhotoResult.Stored`、`PhotoResult.Failed` | 底片、群系、相机冷却 |
| 音乐 | `MusicStopped` | 交给正在演奏的步骤，只在一首放完时发 |
| 邀请 | `Invitation`、`InvitationReply`、`SceneStart`、`SceneOver`、`Withdrawn` | 见第 8 节 |

### 7.3 持久的一半和决定的一半

收件箱随宠物消失，所以一条消息如果会改变要存档的东西，这一部分不能等到下一个 tick 读。这样的消息是 `Message.Durable`：

- 第一半是 `PetMind.keep`，在 `post` 的当时、在服务器线程上执行（会检查线程）。凡是存档的效果都在这里写，也只在这里写：底片和拍过的群系、因这条消息引起的歇息、执照的变化、工资。
- 第二半是 `PetMind.settled`，消息以 `Message.Settled` 的形式进收件箱，下一个 tick 才处理。只管决定和正在做的差事：通知步骤、再决定、让宠物表现出反应。

新增一种带存档效果的消息，要在这两处各加一个分支，并在 `Durable` 的 permits 里加上它。不存档的消息，比如哨声，就不是 `Durable`：宠物在等待期间被卸载，就当没听到，和以前的记忆没有存档是一样的。

### 7.4 Cue

`Cue` 是"立刻、顺便"的反应，不进队列，不移动身体，直接对宠物生效，所以连 AI 关闭的宠物也会做。有两种：

- `Pose`：被拍照的一方转向相机、摆姿势、说一句。
- `Paid`：拿到工资后闪光、高兴、说一句。

瞥一眼要经过执行器，如果当前步骤自己一直在设视线（`holdsGaze`）就跳过。

## 8. 宠物之间的邀请

两只宠物玩一个场景，各自管各自的状态，只靠消息往来，谁也不替对方改记忆、血量、背包。

1. 发起方的 `socialize` 先走 `Invite`，发出 `Invitation`，带场景、搭档序号、自己差事的优先级、过期时间（`reservation_ticks`）。然后 `AwaitReply` 最多等 5 tick。
2. 被邀请方的 `PetMind` 收到后（不是差事回答，因为只有 mind 知道自己此刻在做什么）问 `InvitationDesk.consider`：许可表允许 `SOCIAL`、对这个搭档不在歇息、没有被别人约了、而且发起方的优先级严格高于自己正在做的差事（或什么也没在做）。闲逛（10）接受，干活（50）或捡东西（30）不接受。接受就记下约定，回复 `InvitationReply`，并立刻再决定。
3. 约定一记下，被邀请方的 `cooperate`（80）就是它最高的差事，先停在原地等客人，看着对方。
4. 发起方走过去（`Approach`）。到了，从自己的背包里取出要给的东西，发出 `SceneStart`，之后两边各自演（`PlayPart`）。收到 `SceneStart` 的一方自己回血、自己播吃的声音、自己进入兴奋状态，不由对方代劳。
5. 结束时，发起方把场景演到头就发 `SceneOver`；任何一方中途结束（放弃、被打断、超时）就发 `Withdrawn`，对方在同一个 tick 离开。各自的歇息记在各自的账上。
6. 演奏中的搭档不用邀请：发起方只观察对方是否还在演奏（`ErrandView.playingMusic()`），走过去听即可。

拍照时被拍的朋友摆姿势是单向的，用 `Cue.Pose`，不走邀请。

场景冷却这样写。开始演（`PlayPart` 的第一个 tick）是一次汇报，这一对搭档按这个场景自己的 `scene_cooldown` 歇，之后不管怎么结束都不会缩短它；被拒绝、没人回答、走不到这几种场景没开始的情况，只歇 100 tick（`gave_up` 的值），免得下一口气又去问。

## 9. 状态归属

每一份状态只有一个写入者，这是整个框架最重要的约束，不然同一件事会有两个来源。下表是现在的归属。

| 状态 | 唯一写入者 |
| --- | --- |
| 姿态 `ACTIVITY`、场景 `PERFORMANCE` | `AbstractPet`，由执行器通过 `Projection` 调用 |
| 正在做什么 `INTENT` | `AbstractPet`、`Executor` |
| 走、看、路径 | `LiveHandle` |
| 拉弓、攻击冷却 | `LiveHandle` |
| 歇息的八个存储 | `RestStore`（经 `RestLedger`） |
| 爪里的礼物 | `AbstractPet`、`TakePresent`、`HandOver` |
| 宠物想好的场景 `INTERACTION_PLAN` | `PetSocialSensor`、`Meeting` |
| 乐手演过什么 | `Busk` |
| 农夫看到的五种方块 | `PetFarmerWorkSensor` |
| 攻击目标 | `PetAttackbleEntitySensor` |
| 野生宠物听到的哨声 | `PetMind` |
| 指令 `PetDirective` | 主人的操作（界面、潜行、网络包、手册演示）和 `PetMind`（哨声指令到期时） |
| 别的宠物的大脑、血量、心情、背包 | 没有人。宠物只发消息，对方自己改自己 |
| 工资、执照、底片、群系 | `PetMind.keep` |

这张表由 `StateOwnershipTest` 守着：它扫描 `common/src/main/java`，对每一类写入找出所有写的文件，必须恰好等于表里的写入者。新增一个写入者会失败，写入者不再写了也会失败，要把它从表里去掉。另一项检查是 `errand/impl` 下的差事类不允许出现 `getBrain()`、`getRandom()`、`InitMemory` 和 `setMemory`，它们只能组合步骤。

别的系统要知道宠物在做什么，读 `ErrandView`（`pet.getMind().errands()`）：当前差事、计划、步骤、`seated()`、`inScene()`、`playingMusic()`、被谁邀请过。不要读动画状态，也不要读记忆。

## 10. 数据文件

每个差事一个文件，路径是 `data/<命名空间>/pet_errand/<差事路径>.json`，文件 id 就是差事 id。仓库里这些文件由 `ErrandSettingsData` 通过 `ErrandSettingsProvider` 生成，改数字改 `ErrandSettingsData` 再跑 `:neoforge:runData`、`:fabric:runDatagen`。整合包可以用数据包覆盖任何一个文件。

### 10.1 字段

| 字段 | 意思 |
| --- | --- |
| `priority` | 优先级，非负整数 |
| `score` | 同一层里的基础分，0 到 1 |
| `max_ticks` | 最多做多久，超过就以 `gave_up("timeout")` 结束 |
| `rests` | 歇息，见 6.3：`done`、`gave_up`、`interrupted` 三项必填，`reports` 可选 |
| `yields_to` | 同优先级的差事 id 列表，见 3.5 |
| `overlays` | 叠加层 id 列表，见 4.7 |
| `start_voice` | 开始时说的话，只有打架的差事用（`hunt`），前一个差事是同一类别时不说 |
| `tuning` | 这个差事自己的数字，形状由 `ErrandType.tuningCodec()` 决定，对应 `ErrandTunings` 里的一个类型 |

### 10.2 例子：拍照

这是生成出来的 `take_photo.json`。拍照的歇息大部分是引用，数字在 `pet_camera` 里，这里不重复写：

```json
{
  "max_ticks": 1200,
  "overlays": [],
  "priority": 40,
  "rests": {
    "done": 0,
    "gave_up": { "from": "chiikawa:camera_retry" },
    "interrupted": 0,
    "reports": {
      "failed": { "from": "chiikawa:camera_retry" },
      "stored": { "from": "chiikawa:camera_cooldown" },
      "taken": { "from": "chiikawa:photo_upload_wait" }
    }
  },
  "score": 0.45,
  "tuning": {
    "hold_ticks": 20,
    "look_back_ticks": 60,
    "max_walk_ticks": 400,
    "no_way_ticks": 100,
    "speed": 0.7,
    "stand_back": 4,
    "view_distance": 16.0
  },
  "yields_to": []
}
```

种植用到 `yields_to` 和按对象的歇息：

```json
{
  "max_ticks": 600,
  "priority": 50,
  "rests": {
    "done": 0,
    "gave_up": { "per": "subject", "ticks": 200 },
    "interrupted": 0
  },
  "score": 0.6,
  "tuning": { "no_way_ticks": 0, "reach_sqr": 3.0, "speed": 0.8 },
  "yields_to": [ "chiikawa:harvest" ],
  "overlays": []
}
```

### 10.3 加载和校验

`ErrandSettingsLoader` 在数据重载时读整个目录：

- 文件名不是已注册的差事 id，只警告，跳过。
- 解析失败，这个差事被关掉并报错。关掉的差事不会被开始，不会拖垮世界。
- 字段本身的校验在编解码器里：`priority` 非负、`max_ticks` 为正、`score` 在 0 到 1、`gave_up` 的歇息大于 0、引用的歇息来源已注册、叠加层 id 存在。
- 要看到所有文件才能检查的：`yields_to` 必须指向另一个同优先级的差事。
- 只有差事自己知道的，由 `ErrandType.problem(settings)` 检查，比如 `take_task` 的 `max_ticks` 不能超过公告板预约的有效期。

正在做的差事保存着开始时的那份设置，数据重载只影响下一次开始，不会改变它的时间限制和歇息。

### 10.4 其他文件里的数字

数字只存一处。`pet_camera` 的冷却和重试、`pet_gifting` 的冷却、`pet_interaction` 的预约时间、时长和场景冷却、`pet_anchor` 的区域和跟随距离、音乐配置，仍然在原来的文件里，差事文件用 `from` 引用或者不碰。`pet_personality` 里的 `intent_multipliers` 和 `routine` 用差事 id 作键，键名沿用，所以旧的数据包仍然有效。

## 11. 契约测试

新增差事不能绕过这些测试，缺一项会失败。

### 11.1 JUnit（`common/src/test`）

| 测试 | 管什么 |
| --- | --- |
| `ErrandRegistryContractTest` | 每个差事都有能解码的数据、有 `ErrandFixtures` 里的夹具、每种语言都有名字 |
| `OfferPurityContractTest` | 每个夹具上 `offers` 问两次答案相同，且宠物没变 |
| `StateOwnershipTest` | 第 9 节的归属表 |
| `DecisionCoreTest`、`PetMindDecisionTest`、`AdmissionTest` | 分层、同级不打断、噪声只在层内、拴绳规则 |
| `ExecutorTest`、`RoutineTest` | 结束推迟到步骤之间、`release` 只一次、歇息只写一次、投影清掉、叠加层 |
| `RestLedgerTest` | 结果取最大、汇报替换、按对象、引用 |
| `InboxTest`、`InvitationDeskTest` | 顺序、到期、合并、容量，邀请的接受条件 |
| `ErrandSettingsTest`、`ErrandSettingsDataTest` | 编解码、校验，每个差事都有数据，优先级和歇息是预期的值 |
| 各 `*OfferTest` | 单个差事的开始条件 |

测试用的 `TestView` 是手工构造的 `PetView`，不需要世界和实体。

### 11.2 GameTest（`neoforge/.../gametest`）

`ErrandContractGameTests` 用 `@GameTestGenerator` 给每个差事生成三个用例，场景由 `ErrandScenarios` 提供（一份静态方法，让这个差事成为宠物的最佳选择）：

1. `offer_is_pure`：给宠物拍快照（记忆、背包、同步数据、位置），固定随机数种子，问两次 `offers`，答案相等，快照不变，随机数一次没抽。
2. `ends_in_time`：差事在 `max_ticks` 加 20 tick 内结束，歇息正好等于数据里这种结束方式对应的值。
3. `interrupted_leaves_nothing`：在第一步、中间一步、最后一步各发一次 `Moved`，两个 tick 内以 `interrupted` 结束，歇息等于数据里的 `interrupted`，`Residue.none` 检查没有残留：没有走、看、路径，没有姿态和场景，没有在用物品，没有礼物在爪里，没有占着公告板，没有音乐流，搭档没被约，箱子是关着的。

另有 `every_errand_has_a_scenario`，保证每个差事都有场景。

场景是纯静态方法加普通记录，不依赖具体的 GameTest 注册方式，换版本时只重写注册那一层。

## 12. 新增一个差事

按顺序做：

1. 在 `ErrandIds` 加 id，在 `ErrandCategory` 里选一个类别，没有合适的就加，并在 `PetConstraints.allows` 里写清各指令下的许可。
2. 在 `ErrandTunings` 加调参的类型和编解码器。没有调参的用 `Untuned.NONE`。
3. 在 `errand/impl` 写差事类，实现 `ErrandType`：`offers` 保持纯；`routine` 只用步骤库里的步骤，需要新动作就在 `errand/step` 加步骤，并按第 5 节的规矩写 `release`；`restStore()` 选一个存储，通常用 `RestStore.shared()`。
4. 在 `Errands` 里注册：每个宠物都考虑的放进 `GENERIC` 列表，只有某种能力才有的在静态块里注册，再把 id 加到那个 `PetCapability.errands()` 里（`BasicJob` 等）。
5. 在 `ErrandSettingsData` 加这个差事的数据，写清优先级、分数、`max_ticks`、三种结束的歇息。用到了别处的数字就用 `from`，来源由差事的 `restSources()` 注册。跑 `:neoforge:runData` 和 `:fabric:runDatagen`。
6. 加语言：`intent.chiikawa.<id>` 和每个新原因 `intent.chiikawa.fail.<reason>`，每种语言都要，在 `LanguageData`。
7. 在 `ErrandFixtures` 加夹具（JUnit 用的宠物状态），在 `ErrandScenarios` 加场景（GameTest 用的现场）。
8. 要是差事会改别人的东西，不要直接改：发消息，必要时加一种 `Message`，带存档效果的做成 `Durable`，在 `PetMind.keep` 和 `settled` 里各加一个分支。
9. 要是差事引入了新的写入者，在 `StateOwnershipTest` 的表里写明，不要放宽现有的规则。
10. 跑 `./gradlew.bat assemble test`、两个 datagen、`:neoforge:runGameTestServer`。
