# 0.1.0 技术设计：宠物 AI 解耦重构

> 配套玩法文档：[v0.1.0-gameplay.md](v0.1.0-gameplay.md)
> 基于 1.21.1 分支当前代码（提交 6938eba）。

---

## 1. 目标与范围

**目标**

1. 用"归属、约束、能力、意图"四层模型，取代散落在各个行为和传感器里的状态硬编码。
2. 第一阶段只做重构，玩法和 0.0.9 完全一致。
3. 第二阶段在新框架上实现 0.1.0 玩法：野生吉伊的工具与打工、工作牌、商店、送礼、宠物用品、公告板升级、跟随与召回。

**不在范围内**

- 不替换原版 Brain、记忆、传感器机制，意图层架在 Brain 之上。
- 不改自研渲染和动画管线，只调整动画上下文的输入。
- 不改变现有存档字段的含义。

## 3. 总体模型

```
 归属 Ownership ──┐
 约束 PetDirective ─▶ PetConstraints ──▶ 锚点 + 许可表
 能力 PetCapability ─┐                        │
 性格 Personality ───┼──▶ IntentContext ──▶ IntentSelector ──▶ 选中的 PetIntent ──▶ Brain Activity ──▶ 行为
 传感器写入的记忆 ────┘                                    │
                                                  切换收尾：停止旧行为、清除记忆

 CORE 常驻：漂浮、看向、移动、拴绳（只读锚点）

 行为发出的工作事件 ──▶ TaskTracker ──▶ 工作牌进度、完成到账、粒子
```

**原则**

- **行为只管怎么做，不管该不该做。** 该不该做由许可表、意图的前置条件和打分决定。
- **约束只在一个地方被读取。** AI 里只有 `PetConstraints` 读取 `PetDirective`；动画上下文单独读取它来决定坐下动作。意图拿到的上下文里没有约束本身，只有由它推导出的锚点。
- **主人的指令是过滤，不是分数。** 不允许的意图根本不进入打分，不会因为性格倍率高而压过指令。
- **选择器是唯一切换 Activity 的地方。** 行为、传感器、职业处理都不调用 `setActiveActivity*`。
- **加新玩法等于加一个意图。** 不需要修改任何已有行为。

**明确不做**

- 不在切换职业或约束时重建 Brain。`makeBrain` 一次注册所有 Activity，和现在一样。
- 不给能力加 `enableXxx()` 这类开关方法让通用行为反过来询问。需要改变通用行为时，用意图类别和许可表表达，或者新增一个意图。
- 不为坐下复制一套平行的 Activity。
- 不写集中的 if 阶梯，也不出现"是不是某个能力"的特判。

## 4. 核心类型

### 4.1 归属

不新增字段，直接由 `TamableAnimal` 的驯服状态和主人得出：

```java
public sealed interface PetOwnership {
    record Wild() implements PetOwnership {}
    record Owned(UUID ownerId) implements PetOwnership {}
    static PetOwnership of(AbstractPet pet) { ... }
}
```

### 4.2 约束与锚点

`PetDirective` 取代 `PetMode`，沿用同一个同步字节和存档键，数值含义不变：

```java
public enum PetDirective {
    FOLLOW, // 0，原 FOLLOW
    STAY,   // 1，原 SIT
    FREE;   // 2，原 WORK
}
```

锚点描述宠物被允许活动的范围：

```java
public record PetAnchor(
    GlobalPos center,
    double reach,                 // 意图选取目标（作物、敌人、公告板、商店）的范围
    double leash,                 // 超出后由拴绳强制拉回，始终大于 reach；不拉回时为正无穷
    boolean followsOwner,         // 中心是否为跟随的主人；只有这时落后太远才传送
    boolean canMove
) {
    public boolean withinReach(GlobalPos pos) { ... }
    public boolean withinLeash(GlobalPos pos) { ... }
    public boolean beyondTeleport(GlobalPos pos) { ... }  // followsOwner 且距离不小于 FOLLOW_TELEPORT
}
```

`reach` 和 `leash` 之间的差值是追击余量：开始做一件事要求目标在 `reach` 内，做的过程中允许走到 `leash`，超出 `leash` 才被拉回。这样不会在"追出范围、被拉回、又回去追"之间来回切换。

| 归属 | 约束 | 锚点中心 | reach | leash | 跟随主人 | 能否移动 |
| --- | --- | --- | --- | --- | --- | --- |
| 有主人 | FOLLOW，主人在线、存活、非旁观且同维度，宠物未被拴绳或骑乘 | 主人位置 | `FOLLOW_REACH` | `FOLLOW_LEASH` | 是 | 能 |
| 有主人 | FOLLOW，其他情况 | 宠物当前位置 | 0 | 无 | 否 | 能，只闲逛 |
| 有主人 | STAY | 宠物当前位置 | 0 | 无 | 否 | 不能 |
| 有主人 | FREE | `HOME` 记忆；没有可用的 `HOME` 时为宠物当前位置 | `FREE_REACH` | `FREE_LEASH`；被拴绳或骑乘时无 | 否 | 能 |
| 野生 | 忽略约束 | 生成位置，写入 `HOME`；命令或刷怪蛋生成的没有 `HOME`，为宠物当前位置 | `WILD_REACH` | `WILD_LEASH`；被拴绳或骑乘时无 | 否 | 能 |

初始数值放在一个常量类里，实测后调整。跟随和自由活动的数值沿用 0.0.9 的手感（开始跟随 7 格、传送 20 格、回家 13 格）：

| 常量 | 初始值 |
| --- | --- |
| `FOLLOW_START` | 7 格，`follow_owner` 意图开始靠近主人 |
| `FOLLOW_ARRIVE` | 曼哈顿距离 2 格，`follow_owner` 意图到达主人身边 |
| `FOLLOW_REACH` | 12 格 |
| `FOLLOW_LEASH` | 16 格 |
| `FOLLOW_TELEPORT` | 20 格 |
| `FREE_REACH` | 13 格 |
| `FREE_LEASH` | 20 格 |
| `WILD_REACH` | 24 格 |
| `WILD_LEASH` | 32 格 |

### 4.3 许可表

每个意图属于一个类别。选择器在调用意图的前置条件之前，先用许可表过滤：

```java
public enum IntentCategory { FOLLOW_OWNER, STAY, WANDER, WORK, FORAGE, COMBAT, PICK_UP, TAKE_TASK, SHOP, GIFT }

public final class PetConstraints {
    /** AI 里唯一读取 PetDirective 的类。 */
    public static PetAnchor anchorOf(AbstractPet pet, PetOwnership ownership) { ... }
    public static boolean allows(PetDirective directive, PetOwnership ownership, IntentCategory category) { ... }
}
```

| 意图类别 | 包含的意图 | 跟随 | 坐下 | 自由活动 | 野生 |
| --- | --- | --- | --- | --- | --- |
| `FOLLOW_OWNER` | `follow_owner` | ✓ | ✗ | ✗ | ✗ |
| `STAY` | `stay` | ✗ | ✓ | ✗ | ✗ |
| `WANDER` | `wander` | ✓ | ✗ | ✓ | ✓ |
| `WORK` | `harvest`、`plant`、`deliver`、`play_music` | ✗ | ✗ | ✓ | ✗ |
| `FORAGE` | `weed`、`pick_mushroom` | ✗ | ✗ | ✓ | ✓ |
| `COMBAT` | `melee`、`ranged` | ✗ | ✗ | ✓ | ✓ |
| `PICK_UP` | `pick_up_item` | ✗ | ✗ | ✓ | ✗ |
| `TAKE_TASK` | `take_task` | ✓ | ✗ | ✓ | ✓ |
| `SHOP` | `shop` | ✓ | ✗ | ✓ | ✗ |
| `GIFT` | `gift_owner` | ✓ | ✗ | ✓ | ✗ |

- 跟随状态下的领牌、购物、送礼只会选 `FOLLOW_REACH` 内的公告板和商店，也就是"顺路"。
- 野生宠物不会攻击玩家，由 `PetTargeting.canTarget` 保证；主动索敌只找敌对生物标签，由传感器保证。不需要在许可表里另写。
- 第一阶段只有前七行，跟随、坐下、自由活动三列就是 0.0.9 的行为：跟随时只跟随和闲逛，坐下时不动，自由活动时干活、战斗、拾取。
- 0.0.9 里 36 处模式判断，全部收拢为这张表和 4.2 的锚点表。

### 4.4 能力

`PetCapability` 取代 `IPetJob`，保留数值 id（同步和存档 `PetJob` 继续使用）和优先级：

```java
public interface PetCapability {
    int id();
    int priority();
    boolean canAssume(AbstractPet pet);        // 沿用 BasicJob 的主手工具标签判断
    List<ResourceLocation> intents();          // 该能力提供的意图 id
    Set<ResourceLocation> taskTypes();         // 能领的工作牌类型（第二阶段）
}
```

- `BasicJob`、`MusicianJob`、`NoneJob` 改写为能力实现。
- `refreshJobFromMainhand` 保留，只是返回值类型换成能力。
- 各 `*JobHandler.registerActivities` 保留，改为通过 `PetActivities.register` 注册（见 4.8）。
- 各 `*JobHandler.tickBrain` 删除，里面的判断迁移为意图的前置条件。
- 能力接口不增加任何开关方法。

### 4.5 意图

```java
public interface PetIntent {
    ResourceLocation id();
    IntentCategory category();
    Activity activity();                                   // 通过 PetActivities.register 注册过的 Activity
    IntentCheck canRun(IntentContext ctx);                 // 开始的前置条件
    default IntentCheck canContinue(IntentContext ctx) {   // 进行中的条件，默认与 canRun 相同
        return canRun(ctx);
    }
    float score(IntentContext ctx);                        // 基础分 0 到 1
    default Optional<ResourceLocation> workCounter() { return Optional.empty(); }  // 这件事上报的工作计数，见 7.3
    default void onStop(IntentRuntime runtime) {}          // 切换收尾时调用
    default Set<MemoryModuleType<?>> forgetWhenUnavailable() { return Set.of(); }  // 能力不再提供或许可表不再允许时清除的进度记忆
}

public record IntentCheck(boolean ok, @Nullable String reasonKey) {
    public static final IntentCheck OK = new IntentCheck(true, null);
    public static IntentCheck fail(String reasonKey) { ... }  // 例如 "intent.chiikawa.fail.no_board"
}
```

- 意图对象无状态，所有输入来自 `IntentContext`；每只宠物的执行状态保存在记忆里。
- 进行中的条件可以比开始条件宽松。例如 `melee` 开始要求目标在 `reach` 内，进行中允许目标在 `leash` 内。
- 失败时返回翻译键形式的原因，调试命令和界面直接显示。
- 所有意图注册在 `PetIntents` 注册表里。性格数据加载时校验里面的意图 id，未知 id 打警告。
- `forgetWhenUnavailable` 用于"只在能做这件事时才有意义"的进度，例如乐手记住的"这首已经演过"：离开自由活动或拿走音乐盒后忘掉，回来会重新演奏。
- `workCounter` 是这件事上报的工作计数（例如拔草上报 `chiikawa:weed`）。宠物带着计这种工作的牌时，选择器给它加分，见 4.7。

### 4.6 意图上下文

每次评估时构建一次，分成两部分：

```java
/** 纯数据快照，供 canRun、canContinue、score 使用；测试时可以手工构造。 */
public record IntentContext(
    GlobalPos petPos,
    DayPhase phase,                          // MORNING、DAY、EVENING、NIGHT，由一天中的时间算出
    PetOwnership ownership,
    Personality personality,
    PetAnchor anchor,
    PerceivedTargets targets,                // 传感器记忆的只读快照：攻击目标、作物、容器、野草、蘑菇、可拾取物的位置
    Optional<PetTask> task,                  // 身上的工作牌
    Optional<GlobalPos> offeringBoard,       // 最近的公告板，仅当它有这只宠物能领的牌
    boolean takeTaskCoolingDown,             // 刚才没领到牌，正在歇
    boolean attackCoolingDown,
    boolean hasArrows,
    boolean hasPlayableSelection,            // 音乐盒选的曲子现在会演：没演过，或带着街头演奏牌
    boolean playingMusic
    // 第 9 步加上绿宝石数量、最近的商店、买得起的偏好商品

    public static IntentContext capture(AbstractPet pet) { ... }
}

/** 持有实体，只供切换收尾和步骤执行使用。 */
```

- 快照里没有 `PetDirective`，意图无法绕过许可表去读约束。
- 快照里没有实体和世界，意图无法在打分时顺手改世界。

### 4.7 意图选择器

在 `AbstractPet.customServerAiStep` 中取代 `getJobFromId(...).tickBrain(...)`。

**何时评估**

- 每 `EVAL_INTERVAL`（初始 10 tick）一次，按 `(gameTime + entityId) % EVAL_INTERVAL == 0` 错峰，避免所有宠物挤在同一个 tick。
- 调用 `IntentSelector.requestReevaluate(pet)` 后下一 tick 立即评估。调用时机：主人切换约束、主人给钱或给东西、宠物被攻击、工作牌完成。

**评估步骤**

1. `PetTargeting.clearInvalidAttackTarget` 清除不合法的攻击目标。
2. 构建 `IntentContext`。
3. 检查当前意图，任一条件成立就立即结束它：
   - 当前能力不再提供它；
   - 许可表不再允许它的类别，比如主人刚让宠物坐下；
   - `canContinue` 失败。
4. 候选集合 = 通用意图 + 当前能力提供的意图，依次过滤：许可表、`canRun`。
5. 打分：`(基础分 + 工作牌加分) × 性格倍率 × 时段倍率`，再按容差选择：
   - 工作牌加分 `TASK_BONUS`（0.2）：意图的 `workCounter` 正是身上工作牌计的工作时加上。带着除草牌的农夫先拔草再收割。
   - 容差 = `HOLD_MARGIN`（0.02）+ 性格的 `randomness`。
   - 和最高分相差不超过容差的候选才算"差不多好"。当前意图只要还在容差内就继续做。
   - 否则在"差不多好"的候选里加上最多 ±`randomness` 的扰动排名，选第一。
   - 随机性只在差不多好的选项之间挑，不会让宠物放下手上的事；明显更重要的事超出容差会立刻接管，接管后原意图也抢不回来，所以不会来回抖。
   - 严格顺序（例如"收割优先于种植优先于送货"）不靠分差表达，因为性格倍率会抹平分差；用 `IntentRequirement.yieldsTo` 表达，见 5.2。
6. 最高分和当前意图不同时，执行切换收尾（4.8）。

打分核心是纯函数，便于测试：

```java
static Decision choose(List<Candidate> candidates, @Nullable RunningIntent current, SelectorParams params, RandomSource random) { ... }
```

**记忆**（均不存档，读档后重新评估）

| 记忆 | 内容 |
| --- | --- |
| `CURRENT_INTENT` | 意图 id、开始 tick |
| `INTENT_REEVALUATE` | 存在时下一 tick 立即评估 |
| `INTENT_SWITCH_LOG` | 切换日志，只在调试命令开启时存在 |

### 4.8 切换收尾

**为什么需要：** 原版 `Brain` 切换 Activity 时，只替换活动集合、清除声明过的记忆，不会停止正在运行的行为；`tickEachRunningBehavior` 会继续 tick 所有运行中的行为，直到它自己的 `canStillUse` 为假或超时。0.0.9 在各个行为的 `canStillUse` 里判断 `PetMode.WORK` 就是在弥补这一点。去掉这些判断之后，必须由选择器统一停止旧行为。

**注册：** 意图的 Activity 统一通过一个入口注册：

```java
public final class PetActivities {
    public static void register(Brain<AbstractPet> brain, Activity activity,
                                ImmutableList<Pair<Integer, BehaviorControl<? super AbstractPet>>> behaviors,
                                Set<MemoryModuleType<?>> erasedOnStop) { ... }
    static List<BehaviorControl<? super AbstractPet>> behaviorsOf(Brain<AbstractPet> brain, Activity activity) { ... }
}
```

- 调用原版 `addActivityAndRemoveMemoriesWhenStopped` 声明离开时要清除的记忆，例如战斗清除 `ATTACK_TARGET`。农夫的目标记忆由传感器维护，离开时不清除，被收割打断的种植目标之后还能接着做。
- 注册时不设记忆门槛，前置条件全部放在意图的 `canRun` 里，保证选中哪个意图就一定进入哪个 Activity。
- `behaviorsOf` 通过 mixin accessor 读取原版 `Brain` 自己的行为表。行为是每只宠物各自的实例，不另存一份映射。

**切换顺序：**

1. 调用旧意图的 `onStop`，例如 `play_music` 停止音乐流。
2. `brain.setActiveActivityIfPossible(新 Activity)`，原版随之清除旧 Activity 声明的记忆。
3. 对旧 Activity 中状态为 RUNNING 的行为调用 `doStop`。
4. 清除 `WALK_TARGET`、`PATH`、`LOOK_TARGET`。
5. 写入 `CURRENT_INTENT`，记录切换日志（4.12）。

先清除记忆再停止行为，被打断的行为就不会对已放弃的目标收尾。例如弓手被叫坐下时，不会射出已经拉开的箭。

### 4.9 拴绳

CORE 里保留一个常驻的 `AnchorLeashBehavior`，取代 `KeepAroundBehavior`：

- 只读 `PetAnchor`，不读 `PetDirective`。
- 锚点 `beyondTeleport` 时调用 `teleportToOwner`；宠物超出 `leash` 且当前没有别的行走目标时，走回锚点中心。
- 锚点不能移动（坐下）或没有 `leash` 时什么都不做。
- 被拴绳、骑乘时锚点不跟随主人也不拉回，和 0.0.9 一样。
- `PetUnloadFollow` 用同一个锚点的 `followsOwner` 判断区块卸载前是否把宠物传送到主人身边。

拴绳是硬保证，意图负责平时的活动：跟随时由 `follow_owner` 意图在 7 格外靠近主人，自由活动时意图只会选 `reach` 内的目标。

### 4.10 长意图

需要走过去再做一件事的意图（领牌，第 9 步的购物、送礼），由它的 Activity 里的一个行为从头做到尾，不另做通用的步骤机制和冷却表：

- **走过去再做：** 行为开始时先占住要用的东西（例如预约牌位），设行走目标；到了就立刻办完（领牌），没有需要护住的"不可打断步骤"。
- **被打断：** 切换收尾停止行为，行为在 `stop` 里放掉占住的东西。
- **失败歇一会儿：** 行为没办成（走不到、牌没了、被打断）就写一个带过期时间的记忆（领牌是 `TAKE_TASK_COOLDOWN`，600 tick），意图的前置条件看到它就不开始，宠物不会马上回头再试。这是原版 `ATTACK_COOLING_DOWN` 的做法。
- **长期进度**只存在工作牌 `PetTask` 和公告板方块实体里，读档后行为从头来。

### 4.11 性格

数据驱动，每种宠物实体一份，路径 `data/chiikawa/pet_personality/<entity>.json`，由 datagen 生成：

```json
{
  "intent_multipliers": {
    "chiikawa:take_task": 1.0,
    "chiikawa:shop": 0.6,
    "chiikawa:gift_owner": 0.8
  },
  "routine": {
    "MORNING": { "chiikawa:take_task": 1.3 },
    "NIGHT": { "chiikawa:wander": 0.5 }
  },
  "randomness": 0.1,
  "likes": ["#chiikawa:pet_likes/snacks"],     // 商店那一步再加
  "wild_tools": [
    { "item": "minecraft:wooden_hoe", "weight": 6 },
    { "item": "chiikawa:chiikawa_weapon", "weight": 2 },
    { "item": "minecraft:air", "weight": 1 }
  ]
}
```

- `routine` 按时段调整倍率。不给 Brain 设置原版 `Schedule`，否则会多出一个切换 Activity 的地方。
- 通过数据包重载监听器加载，使用 Codec 解析；缺失时回退到默认性格。
- 客户端不需要这份数据。

### 4.12 调试

- **调试命令：** `/chiikawa debug intent` 对准星所指的宠物输出当前意图及已运行时长，以及每个候选意图：许可表是否允许、`canRun` 结果与失败原因、分数；第二阶段加上冷却剩余和当前步骤。`/chiikawa debug intent log on|off` 开关切换日志，`log` 查看。
- **切换日志：** 每只宠物一个环形缓冲，保留最近 20 次切换，记录 tick、从哪个意图到哪个意图、触发方式（周期、重评请求、条件失败、步骤超时）、前三名分数。平时关闭，由调试命令开启。
- **玩家可见：** 背包界面显示当前在做什么，意图失败时显示原因，例如"公告板不在范围内"（阶段二）。

- `play_music` 的 `onStop` 负责原来 `clearMusicState` 做的事。

## 6. 传感器

- **原则：** 传感器只采集信息，不判断约束、归属和职业；按目标种类写入各自的记忆，由意图决定用不用。
- **现有传感器调整：**
  - `PetFarmerWorkSensor`：去掉模式判断，分别写入 `HARVEST_POS`、`PLANT_POS`、`CONTAINER_POS`、`WEED_POS`、`MUSHROOM_POS`，不分昼夜和归属。野生宠物不收割作物，是因为许可表不允许野生宠物的 `WORK` 类别；夜里才采蘑菇，是 `pick_mushroom` 的前置条件。都不在传感器里判断。野草和蘑菇用方块标签 `entity_weeds`（矮草、高草、蕨、大型蕨）和 `entity_mushrooms`（红、棕蘑菇）。
  - `PetAttackbleEntitySensor`：去掉模式判断，保留目标合法性过滤和受击反击。
  - `PetPickableItemSensor`：去掉模式和驯服判断。
- **避免空转：** 传感器在当前能力用不上它的结果时跳过扫描，例如非农夫不扫描作物。这是性能判断，结果不影响行为。
- **遗忘远目标：** 农夫传感器忘掉离宠物超过 10 格的目标。意图只用 `reach` 内的目标，而传感器有目标时不会再扫描，不忘掉的话宠物会卡在一个用不上的目标上。
- **第一阶段的已知差异：** 跟随或坐下时，剑士和弓手的传感器也会记住附近的敌人，切到自由活动后会立刻开打。
- **新增传感器：** `PetBoardSensor` 每 40 tick 通过原版 `PoiManager` 查找 48 格内最近的公告板，写入记忆 `NEAREST_BOARD`；够不够得着由 `take_task` 按锚点判断。商店在第 9 步用同样的方式加。
- **POI 类型：** 公告板和商店注册为 POI 类型，查询开销和村民找工作方块相同。

## 7. 工作牌

代码在 `task` 包里：牌型、工作牌、公告板规则和到账都在这里，公告板方块在 `block` 包。

### 7.1 牌型数据

路径 `data/chiikawa/pet_task/<id>.json`，由 datagen（`PetTaskTypeData`）生成，`PetTaskTypeLoader` 加载：

```json
{
  "capability": "chiikawa:farmer",
  "counter": "chiikawa:weed",
  "amount": { "type": "minecraft:uniform", "min_inclusive": 8, "max_inclusive": 16 },
  "reward": "chiikawa:pet_task/weeding",
  "weight": 3
}
```

- `capability` 为能力的注册 id，`counter` 为工作计数（7.3），`amount` 是原版整数提供器，`reward` 为战利品表，`weight` 是公告板抽到它的权重。
- 能力或工作计数不存在时加载会打警告；解析失败的文件跳过。
- 不设"时间"字段：夜里才采蘑菇由 `pick_mushroom` 意图的前置条件决定，不在牌上再写一遍。
- 已有牌型：除草（农夫，8–16 株，权重 3）、夜间采蘑菇（农夫，4–8 朵，权重 2）、街头演奏（乐手，120–240 秒，权重 1）。讨伐随公告板升级加入（第 10 步）。
- 报酬以绿宝石为主，30% 概率附带面包、蘑菇煲或曲奇。

### 7.2 工作牌

```java
public record PetTask(ResourceLocation type, ResourceLocation capability, ResourceLocation counter,
                      int target, ResourceKey<LootTable> reward, int progress) {}
```

- 同一个记录既是公告板上的牌，也是宠物身上的牌。牌自带计数、目标和报酬，数据包重载不会让已领的牌失效。
- 宠物身上存在同步数据里（存档键 `Task`），客户端据此渲染挂在肩上的小木牌、在背包界面显示进度。当前意图也同步一份，供背包界面显示"正在做什么"。
- 宠物死亡时在 `die` 里清掉，玩偶里不带失败的牌，复活也就不带。

### 7.3 工作计数与到账

`PetWorkCounters` 定义工作计数：`chiikawa:weed`、`chiikawa:pick_mushroom`、`chiikawa:play_music_second`；讨伐的 `kill_hostile` 随讨伐牌加入。

| 工作计数 | 在哪里上报 |
| --- | --- |
| `chiikawa:weed` | `CollectBlockBehavior` 拔掉一株草后 |
| `chiikawa:pick_mushroom` | `CollectBlockBehavior` 采下一朵蘑菇后 |
| `chiikawa:play_music_second` | `PlayMusicBehavior` 演奏中每秒一次 |

`TaskTracker.advance(pet, counter, amount)`：

1. 计数与身上牌的 `counter` 一致时累加进度。
2. 做满时按战利品表生成报酬放进背包，放不下的掉在脚下。
3. 冒出开心村民的绿色闪光粒子，触发 `PetReaction.HAPPY` 和开心语音。
4. 清掉牌并请求重评，当天还有对口的牌就会再去领。

带着街头演奏牌的乐手会反复演奏选好的曲子，直到牌做满。

### 7.4 公告板

`LaborBoardBlock` 是可合成的朝向方块（纸、木板、木棍），`LaborBoardBlockEntity` 保存当天的日序号和牌位列表，每个牌位是一张牌、预约（宠物 UUID、过期时间）和是否已被领走。规则在纯逻辑类 `BoardSlips` 里：

- **每日刷新：** 不在 tick 里刷新；当天第一次被查看时生成 3 张牌。种子由世界种子、日序号和方块坐标组合而成，同一块板同一天所有人看到的一样。
- **找牌：** 先找这只宠物自己预约着的；否则找第一张对口、没被领走、没被别的宠物预约的。
- **野生靠后：** 野生宠物要到日出后 12000 tick 才会去领，只领有主人的宠物剩下的。
- **预约：** 出发时占住一张牌，1200 tick 后自动失效，其他宠物不会奔向同一张。
- **领取：** 走到离公告板 3 格内时领走，牌从板上消失。
- **没领到：** 放掉预约，歇 600 tick（4.10）。
- **领走的记下来：** 牌位记下领走它的宠物名和主人名，界面据此显示。

**界面：** 右键公告板，服务端把当天的牌发给这名玩家（`BoardPayloads`），客户端打开 `LaborBoardScreen`：每张牌显示牌型、目标数量、给哪个职业，以及"还没人领"或"谁领走了"。界面只读，牌由宠物自己去领。

第 10 步加公告板升级。

## 8. 商店与送礼

### 8.1 商店

- `ShopBlockEntity` 注册为 POI。
- 价目表路径 `data/chiikawa/shop_catalog/<id>.json`：

```json
{
  "entries": [
    { "item": "minecraft:cookie", "buy": 1, "sell": 0, "tags": ["chiikawa:pet_likes/snacks"] },
    { "item": "minecraft:wheat", "buy": 0, "sell": 1 }
  ]
}
```

- 主人通过交易界面买卖；`buy` 为 0 表示不出售，`sell` 为 0 表示不收购。

### 8.2 宠物购物

`shop` 意图按 4.10 的步骤执行：

1. 从性格偏好和价目表的交集里，挑出买得起的商品，决定给自己买还是买礼物。
2. 走到商店。
3. 扣除背包里的绿宝石，把商品放进背包。
4. 买给自己的立即使用（食物吃掉、用品装备）；买给主人的标记为待送礼物，交给 `gift_owner`。

### 8.3 送礼

`gift_owner` 意图：走到主人身边，把礼物放进主人物品栏（满了就掉在主人脚下），播放递出动作、开心反应和语音。完成后进入冷却。

### 8.4 主人给东西

`PetInteractHandler` 增加：主人手持绿宝石右键时放进宠物背包；手持宠物用品或食物右键时交给宠物使用。两者都触发开心反应并请求重评。

## 9. 野生吉伊

- **生成：** 在 `finalizeSpawn` 中，自然生成和区块生成的野生宠物按性格的 `wild_tools` 抽取工具放进主手（背包第一格），设置 `PetDirective.FREE`。
- **驯服：** 重写 `tame`，驯服成功后设置为 `FOLLOW`，背包内容保持不变。
- **家的位置：** `AbstractPet.settleHome` 是唯一的家规则：自由活动以当前位置为 `HOME`，跟随清除 `HOME`，坐下保留。`setPetDirective`（交互切换、野生生成、驯服）和复活仪式都调用它，所以复活的自由活动宠物以蛋糕位置为新家。
- **死亡掉落：** `getEquipmentDropChance` 对所有槽位返回 0，工具和装备完整留在玩偶里，有主人和野生的宠物都一样。
- **时段：** MORNING 23000–3000，DAY 3000–12000，EVENING 12000–13000，NIGHT 13000–23000；没有昼夜循环的维度用它的固定时间，例如下界算夜晚。

## 10. 界面

界面全部用代码画，不用贴图，风格一处说了算，所以加一块面板不用再画图。

### 10.1 `:ui` 模块

`ui` 是个独立的 Gradle 子工程，只依赖 JDK，编译期看不到 Minecraft。两个 loader 像编译 `common` 那样把它的源码编进成品（`uiJava` 配置），所以成品里没有多出一个库。

- `DrawSurface`：整个模块跟游戏之间只有这一个接口——`fillRect`、`drawText`、`textWidth`、`lineHeight`。
- `UiTheme` 管颜色（奶油棕：底 `#F7E9D2`，描边 `#A9754F`，字 `#5A3A2B`），`UiStyle` 管间距和尺寸。改风格就改这两个文件。
- `Ui` 是部件：`panel`、`titledPanel`、`divider`、`textRight`、`textClipped`、`chip`。`TextClip` 负责按宽度截字加省略号。
- 模块自己有单元测试，用一个假的 `DrawSurface` 记下画了哪些矩形和文字，断言的是坐标，不用起游戏。

游戏这边有两个实现，都在 `client.ui.mc` 里：`GuiSurface` 包 `GuiGraphics`，给各个 Screen 用；`WorldSurface` 包 `PoseStack` 和 `MultiBufferSource`，把同样的部件画到世界里。

### 10.2 头顶标签

主人走到 12 格内，自家宠物头顶显示在做什么（`PetStatusText.label`，闲着且没牌时不显示），按 F1 一起隐藏，别人的宠物不显示。

标签就是 `Ui.chip`，画在朝向摄像机、缩到文字像素的面上。底条走 `RenderType.textBackground()`，文字走 `Font.DisplayMode.POLYGON_OFFSET`，两者都测深度，所以隔着墙看不见。这一对是原版自己的搭配：文字显示实体和告示牌上的字都这么画。不能用原版名牌那套底色，它画在自己字形的前面，只有 see-through 模式才正常，而 see-through 正是隔墙可见；也不要靠给底条加 z 偏移来让位，差一点就会在走动时闪，多边形偏移是硬件层面办这件事的。

宠物拿着工作牌时，肩上挂一块小木牌（`SlipTagLayer`，挂在胸前实体坐标 y 4.5、z -4.8），远看就知道它在打工。

## 13. 测试

- **单元测试：**
  - `PetConstraints`：五种归属与约束组合的锚点；许可表的每一格。
  - `IntentSelector.choose`：许可表过滤、打分、保持加分、最短停留、随机扰动（注入固定随机源）；第二阶段加上冷却过滤、不可打断步骤、步骤超时。

  - `TaskTracker`：进度累加、完成、事件不匹配、死亡清除。
