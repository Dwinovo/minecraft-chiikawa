# 0.1.0 技术设计：宠物 AI 解耦重构

> 配套玩法文档：[v0.1.0-gameplay.md](v0.1.0-gameplay.md)
> 基于 1.21.1 分支当前代码（提交 6938eba）。

---

## 1. 目标与范围

**目标**

1. 用"归属、约束、能力、意图"四层模型，取代散落在各个行为和传感器里的状态硬编码。
2. 第一阶段只做重构，玩法和 0.0.9 完全一致。
3. 第二阶段在新框架上实现 0.1.0 玩法：野生吉伊的工具与打工、工作牌、商店、送礼、宠物用品、公告板升级、跟随与召回。

**不在范围内**

- 不替换原版 Brain、记忆、传感器机制，意图层架在 Brain 之上。
- 不改自研渲染和动画管线，只调整动画上下文的输入。
- 不改变现有存档字段的含义。

## 3. 总体模型

```
 归属 Ownership ──┐
 约束 PetDirective ─▶ PetConstraints ──▶ 锚点 + 许可表
 能力 PetCapability ─┐                        │
 性格 Personality ───┼──▶ IntentContext ──▶ IntentSelector ──▶ 选中的 PetIntent ──▶ Brain Activity ──▶ 行为
 传感器写入的记忆 ────┘                                    │
                                                  切换收尾：停止旧行为、清除记忆

 CORE 常驻：漂浮、看向、移动、拴绳（只读锚点）

 行为发出的工作事件 ──▶ TaskTracker ──▶ 工作牌进度、完成到账、粒子
```

**原则**

- **行为只管怎么做，不管该不该做。** 该不该做由许可表、意图的前置条件和打分决定。
- **约束只在一个地方被读取。** AI 里只有 `PetConstraints` 读取 `PetDirective`；动画上下文单独读取它来决定坐下动作。意图拿到的上下文里没有约束本身，只有由它推导出的锚点。
- **主人的指令是过滤，不是分数。** 不允许的意图根本不进入打分，不会因为性格倍率高而压过指令。
- **选择器是唯一切换 Activity 的地方。** 行为、传感器、职业处理都不调用 `setActiveActivity*`。
- **加新玩法等于加一个意图。** 不需要修改任何已有行为。

**明确不做**

- 不在切换职业或约束时重建 Brain。`makeBrain` 一次注册所有 Activity，和现在一样。
- 不给能力加 `enableXxx()` 这类开关方法让通用行为反过来询问。需要改变通用行为时，用意图类别和许可表表达，或者新增一个意图。
- 不为坐下复制一套平行的 Activity。
- 不写集中的 if 阶梯，也不出现"是不是某个能力"的特判。

## 4. 核心类型

### 4.1 归属

不新增字段，直接由 `TamableAnimal` 的驯服状态和主人得出：

```java
public sealed interface PetOwnership {
    record Wild() implements PetOwnership {}
    record Owned(UUID ownerId) implements PetOwnership {}
    static PetOwnership of(AbstractPet pet) { ... }
}
```

### 4.2 约束与锚点

`PetDirective` 取代 `PetMode`，沿用同一个同步字节和存档键，数值含义不变：

```java
public enum PetDirective {
    FOLLOW, // 0，原 FOLLOW
    STAY,   // 1，原 SIT
    FREE;   // 2，原 WORK
}
```

锚点描述宠物被允许活动的范围：

```java
public record PetAnchor(
    GlobalPos center,
    double reach,                 // 意图选取目标（作物、敌人、公告板、商店）的范围
    double leash,                 // 超出后由拴绳强制拉回，始终大于 reach；不拉回时为正无穷
    boolean followsOwner,         // 中心是否为跟随的主人；只有这时落后太远才传送
    boolean canMove
) {
    public boolean withinReach(GlobalPos pos) { ... }
    public boolean withinLeash(GlobalPos pos) { ... }
    public boolean beyondTeleport(GlobalPos pos) { ... }  // followsOwner 且距离不小于 FOLLOW_TELEPORT
}
```

`reach` 和 `leash` 之间的差值是追击余量：开始做一件事要求目标在 `reach` 内，做的过程中允许走到 `leash`，超出 `leash` 才被拉回。这样不会在"追出范围、被拉回、又回去追"之间来回切换。

| 归属 | 约束 | 锚点中心 | reach | leash | 跟随主人 | 能否移动 |
| --- | --- | --- | --- | --- | --- | --- |
| 有主人 | FOLLOW，主人在线、存活、非旁观且同维度，宠物未被拴绳或骑乘 | 主人位置 | `FOLLOW_REACH` | `FOLLOW_LEASH` | 是 | 能 |
| 有主人 | FOLLOW，其他情况 | 宠物当前位置 | 0 | 无 | 否 | 能，只闲逛 |
| 有主人 | STAY | 宠物当前位置 | 0 | 无 | 否 | 不能 |
| 有主人 | FREE | `HOME` 记忆；没有可用的 `HOME` 时为宠物当前位置 | `FREE_REACH` | `FREE_LEASH`；被拴绳或骑乘时无 | 否 | 能 |
| 野生 | 忽略约束 | 生成位置，写入 `HOME`；命令或刷怪蛋生成的没有 `HOME`，为宠物当前位置 | `WILD_REACH` | `WILD_LEASH`；被拴绳或骑乘时无 | 否 | 能 |

初始数值放在一个常量类里，实测后调整。跟随和自由活动的数值沿用 0.0.9 的手感（开始跟随 7 格、传送 20 格、回家 13 格）：

| 常量 | 初始值 |
| --- | --- |
| `FOLLOW_START` | 7 格，`follow_owner` 意图开始靠近主人 |
| `FOLLOW_ARRIVE` | 曼哈顿距离 2 格，`follow_owner` 意图到达主人身边 |
| `FOLLOW_REACH` | 12 格 |
| `FOLLOW_LEASH` | 16 格 |
| `FOLLOW_TELEPORT` | 20 格 |
| `FREE_REACH` | 13 格 |
| `FREE_LEASH` | 20 格 |
| `WILD_REACH` | 24 格 |
| `WILD_LEASH` | 32 格 |

### 4.3 许可表

每个意图属于一个类别。选择器在调用意图的前置条件之前，先用许可表过滤：

```java
public enum IntentCategory { FOLLOW_OWNER, STAY, WANDER, WORK, FORAGE, COMBAT, PICK_UP, TAKE_TASK, SHOP, GIFT }

public final class PetConstraints {
    /** AI 里唯一读取 PetDirective 的类。 */
    public static PetAnchor anchorOf(AbstractPet pet, PetOwnership ownership) { ... }
    public static boolean allows(PetDirective directive, PetOwnership ownership, IntentCategory category) { ... }
}
```

| 意图类别 | 包含的意图 | 跟随 | 坐下 | 自由活动 | 野生 |
| --- | --- | --- | --- | --- | --- |
| `FOLLOW_OWNER` | `follow_owner` | ✓ | ✗ | ✗ | ✗ |
| `STAY` | `stay` | ✗ | ✓ | ✗ | ✗ |
| `WANDER` | `wander` | ✓ | ✗ | ✓ | ✓ |
| `WORK` | `harvest`、`plant`、`deliver`、`play_music` | ✗ | ✗ | ✓ | ✗ |
| `FORAGE` | `weed`、`pick_mushroom` | ✗ | ✗ | ✓ | ✓ |
| `COMBAT` | `melee`、`ranged` | ✗ | ✗ | ✓ | ✓ |
| `PICK_UP` | `pick_up_item` | ✗ | ✗ | ✓ | ✗ |
| `TAKE_TASK` | `take_task` | ✓ | ✗ | ✓ | ✓ |
| `SHOP` | `shop` | ✓ | ✗ | ✓ | ✗ |
| `GIFT` | `gift_owner` | ✓ | ✗ | ✓ | ✗ |

- 跟随状态下的领牌、购物、送礼只会选 `FOLLOW_REACH` 内的公告板和商店，也就是"顺路"。
- 野生宠物不会攻击玩家，由 `PetTargeting.canTarget` 保证；主动索敌只找敌对生物标签，由传感器保证。不需要在许可表里另写。
- 第一阶段只有前七行，跟随、坐下、自由活动三列就是 0.0.9 的行为：跟随时只跟随和闲逛，坐下时不动，自由活动时干活、战斗、拾取。
- 0.0.9 里 36 处模式判断，全部收拢为这张表和 4.2 的锚点表。

### 4.4 能力

`PetCapability` 取代 `IPetJob`，保留数值 id（同步和存档 `PetJob` 继续使用）和优先级：

```java
public interface PetCapability {
    int id();
    int priority();
    boolean canAssume(AbstractPet pet);        // 沿用 BasicJob 的主手工具标签判断
    List<ResourceLocation> intents();          // 该能力提供的意图 id
    Set<ResourceLocation> taskTypes();         // 能领的工作牌类型（第二阶段）
}
```

- `BasicJob`、`MusicianJob`、`NoneJob` 改写为能力实现。
- `refreshJobFromMainhand` 保留，只是返回值类型换成能力。
- 各 `*JobHandler.registerActivities` 保留，改为通过 `PetActivities.register` 注册（见 4.8）。
- 各 `*JobHandler.tickBrain` 删除，里面的判断迁移为意图的前置条件。
- 能力接口不增加任何开关方法。

### 4.5 意图

```java
public interface PetIntent {
    ResourceLocation id();
    IntentCategory category();
    Activity activity();                                   // 通过 PetActivities.register 注册过的 Activity
    IntentCheck canRun(IntentContext ctx);                 // 开始的前置条件
    default IntentCheck canContinue(IntentContext ctx) {   // 进行中的条件，默认与 canRun 相同
        return canRun(ctx);
    }
    float score(IntentContext ctx);                        // 基础分 0 到 1
    default Optional<ResourceLocation> workCounter() { return Optional.empty(); }  // 这件事上报的工作计数，见 7.3
    default void onStop(IntentRuntime runtime) {}          // 切换收尾时调用
    default Set<MemoryModuleType<?>> forgetWhenUnavailable() { return Set.of(); }  // 能力不再提供或许可表不再允许时清除的进度记忆
}

public record IntentCheck(boolean ok, @Nullable String reasonKey) {
    public static final IntentCheck OK = new IntentCheck(true, null);
    public static IntentCheck fail(String reasonKey) { ... }  // 例如 "intent.chiikawa.fail.no_board"
}
```

- 意图对象无状态，所有输入来自 `IntentContext`；每只宠物的执行状态保存在记忆里。
- 进行中的条件可以比开始条件宽松。例如 `melee` 开始要求目标在 `reach` 内，进行中允许目标在 `leash` 内。
- 失败时返回翻译键形式的原因，调试命令和界面直接显示。
- 所有意图注册在 `PetIntents` 注册表里。性格数据加载时校验里面的意图 id，未知 id 打警告。
- `forgetWhenUnavailable` 用于"只在能做这件事时才有意义"的进度，例如乐手记住的"这首已经演过"：离开自由活动或拿走音乐盒后忘掉，回来会重新演奏。
- `workCounter` 是这件事上报的工作计数（例如拔草上报 `chiikawa:weed`）。宠物带着计这种工作的牌时，选择器给它加分，见 4.7。

### 4.6 意图上下文

每次评估时构建一次，分成两部分：

```java
/** 纯数据快照，供 canRun、canContinue、score 使用；测试时可以手工构造。 */
public record IntentContext(
    GlobalPos petPos,
    DayPhase phase,                          // MORNING、DAY、EVENING、NIGHT，由一天中的时间算出
    PetOwnership ownership,
    Personality personality,
    PetAnchor anchor,
    PerceivedTargets targets,                // 传感器记忆的只读快照：攻击目标、作物、容器、野草、蘑菇、可拾取物的位置
    Optional<PetTask> task,                  // 身上的工作牌
    Optional<GlobalPos> offeringBoard,       // 最近的公告板，仅当它有这只宠物能领的牌
    boolean takeTaskCoolingDown,             // 刚才没领到牌，正在歇
    boolean attackCoolingDown,
    boolean hasArrows,
    boolean hasPlayableSelection,            // 音乐盒选的曲子现在会演：没演过，或带着街头演奏牌
    boolean playingMusic
    // 第 9 步加上绿宝石数量、最近的商店、买得起的偏好商品

/** 持有实体，只供切换收尾和步骤执行使用。 */
```

- 快照里没有 `PetDirective`，意图无法绕过许可表去读约束。
- 快照里没有实体和世界，意图无法在打分时顺手改世界。

### 4.7 意图选择器

在 `AbstractPet.customServerAiStep` 中取代 `getJobFromId(...).tickBrain(...)`。

**何时评估**

- 每 `EVAL_INTERVAL`（初始 10 tick）一次，按 `(gameTime + entityId) % EVAL_INTERVAL == 0` 错峰，避免所有宠物挤在同一个 tick。
- 调用 `IntentSelector.requestReevaluate(pet)` 后下一 tick 立即评估。调用时机：主人切换约束、主人给钱或给东西、宠物被攻击、工作牌完成。

**评估步骤**

1. `PetTargeting.clearInvalidAttackTarget` 清除不合法的攻击目标。
2. 构建 `IntentContext`。
3. 检查当前意图，任一条件成立就立即结束它：
   - 当前能力不再提供它；
   - 许可表不再允许它的类别，比如主人刚让宠物坐下；
   - `canContinue` 失败。
4. 候选集合 = 通用意图 + 当前能力提供的意图，依次过滤：许可表、`canRun`。
5. 打分：`(基础分 + 工作牌加分) × 性格倍率 × 时段倍率`，再按容差选择：
   - 工作牌加分 `TASK_BONUS`（0.2）：意图的 `workCounter` 正是身上工作牌计的工作时加上。带着除草牌的农夫先拔草再收割。
   - 容差 = `HOLD_MARGIN`（0.02）+ 性格的 `randomness`。
   - 和最高分相差不超过容差的候选才算"差不多好"。当前意图只要还在容差内就继续做。
   - 否则在"差不多好"的候选里加上最多 ±`randomness` 的扰动排名，选第一。
   - 随机性只在差不多好的选项之间挑，不会让宠物放下手上的事；明显更重要的事超出容差会立刻接管，接管后原意图也抢不回来，所以不会来回抖。
   - 严格顺序（例如"收割优先于种植优先于送货"）不靠分差表达，因为性格倍率会抹平分差；用 `IntentRequirement.yieldsTo` 表达，见 5.2。
6. 最高分和当前意图不同时，执行切换收尾（4.8）。

打分核心是纯函数，便于测试：

```java
static Decision choose(List<Candidate> candidates, @Nullable RunningIntent current, SelectorParams params, RandomSource random) { ... }
```

**记忆**（均不存档，读档后重新评估）

| 记忆 | 内容 |
| --- | --- |
| `CURRENT_INTENT` | 意图 id、开始 tick |
| `INTENT_REEVALUATE` | 存在时下一 tick 立即评估 |
| `INTENT_SWITCH_LOG` | 切换日志，只在调试命令开启时存在 |

### 4.8 切换收尾

**为什么需要：** 原版 `Brain` 切换 Activity 时，只替换活动集合、清除声明过的记忆，不会停止正在运行的行为；`tickEachRunningBehavior` 会继续 tick 所有运行中的行为，直到它自己的 `canStillUse` 为假或超时。0.0.9 在各个行为的 `canStillUse` 里判断 `PetMode.WORK` 就是在弥补这一点。去掉这些判断之后，必须由选择器统一停止旧行为。

**注册：** 意图的 Activity 统一通过一个入口注册：

```java
public final class PetActivities {
    public static void register(Brain<AbstractPet> brain, Activity activity,
                                ImmutableList<Pair<Integer, BehaviorControl<? super AbstractPet>>> behaviors,
                                Set<MemoryModuleType<?>> erasedOnStop) { ... }
    static List<BehaviorControl<? super AbstractPet>> behaviorsOf(Brain<AbstractPet> brain, Activity activity) { ... }
}
```

- 调用原版 `addActivityAndRemoveMemoriesWhenStopped` 声明离开时要清除的记忆，例如战斗清除 `ATTACK_TARGET`。农夫的目标记忆由传感器维护，离开时不清除，被收割打断的种植目标之后还能接着做。
- 注册时不设记忆门槛，前置条件全部放在意图的 `canRun` 里，保证选中哪个意图就一定进入哪个 Activity。
- `behaviorsOf` 通过 mixin accessor 读取原版 `Brain` 自己的行为表。行为是每只宠物各自的实例，不另存一份映射。

**切换顺序：**

1. 调用旧意图的 `onStop`，例如 `play_music` 停止音乐流。
2. `brain.setActiveActivityIfPossible(新 Activity)`，原版随之清除旧 Activity 声明的记忆。
3. 对旧 Activity 中状态为 RUNNING 的行为调用 `doStop`。
4. 清除 `WALK_TARGET`、`PATH`、`LOOK_TARGET`。
5. 写入 `CURRENT_INTENT`，记录切换日志（4.12）。

先清除记忆再停止行为，被打断的行为就不会对已放弃的目标收尾。例如弓手被叫坐下时，不会射出已经拉开的箭。

### 4.9 拴绳

CORE 里保留一个常驻的 `AnchorLeashBehavior`，取代 `KeepAroundBehavior`：

- 只读 `PetAnchor`，不读 `PetDirective`。
- 宠物超出 `leash` 且当前没有别的行走目标时，走回锤点中心（**不再在这里传送**，见 11.5）。
- 锚点不能移动（坐下）或没有 `leash` 时什么都不做。
- 被拴绳、骑乘时锚点不跟随主人也不拉回，和 0.0.9 一样。
- `PetFollowKeeper` 与 `PetUnloadFollow` 用同一个锤点判断要不要把宠物传送到主人身边。

拴绳是硬保证，意图负责平时的活动：跟随时由 `follow_owner` 意图在 7 格外靠近主人，自由活动时意图只会选 `reach` 内的目标。

### 4.10 长意图

需要走过去再做一件事的意图（领牌，第 9 步的购物、送礼），由它的 Activity 里的一个行为从头做到尾，不另做通用的步骤机制和冷却表：

- **走过去再做：** 行为开始时先占住要用的东西（例如预约牌位），设行走目标；到了就立刻办完（领牌），没有需要护住的"不可打断步骤"。
- **被打断：** 切换收尾停止行为，行为在 `stop` 里放掉占住的东西。
- **失败歇一会儿：** 行为没办成（走不到、牌没了、被打断）就写一个带过期时间的记忆（领牌是 `TAKE_TASK_COOLDOWN`，600 tick），意图的前置条件看到它就不开始，宠物不会马上回头再试。这是原版 `ATTACK_COOLING_DOWN` 的做法。
- **长期进度**只存在工作牌 `PetTask` 和公告板方块实体里，读档后行为从头来。

### 4.11 性格

数据驱动，每种宠物实体一份，路径 `data/chiikawa/pet_personality/<entity>.json`，由 datagen 生成：

```json
{
  "intent_multipliers": {
    "chiikawa:take_task": 1.0,
    "chiikawa:shop": 0.6,
    "chiikawa:gift_owner": 0.8
  },
  "routine": {
    "MORNING": { "chiikawa:take_task": 1.3 },
    "NIGHT": { "chiikawa:wander": 0.5 }
  },
  "randomness": 0.1,
  "likes": ["#chiikawa:pet_likes/snacks"],     // 商店那一步再加
  "wild_tools": [
    { "item": "minecraft:wooden_hoe", "weight": 6 },
    { "item": "chiikawa:chiikawa_weapon", "weight": 2 },
    { "item": "minecraft:air", "weight": 1 }
  ]
}
```

- `routine` 按时段调整倍率。不给 Brain 设置原版 `Schedule`，否则会多出一个切换 Activity 的地方。
- 通过数据包重载监听器加载，使用 Codec 解析；缺失时回退到默认性格。
- 客户端不需要这份数据。

### 4.12 调试

- **调试命令：** `/chiikawa debug intent` 对准星所指的宠物输出当前意图及已运行时长，以及每个候选意图：许可表是否允许、`canRun` 结果与失败原因、分数；第二阶段加上冷却剩余和当前步骤。`/chiikawa debug intent log on|off` 开关切换日志，`log` 查看。
- **切换日志：** 每只宠物一个环形缓冲，保留最近 20 次切换，记录 tick、从哪个意图到哪个意图、触发方式（周期、重评请求、条件失败、步骤超时）、前三名分数。平时关闭，由调试命令开启。
- **玩家可见：** 背包界面显示当前在做什么，意图失败时显示原因，例如"公告板不在范围内"（阶段二）。

### 4.13 战斗

写法参考 Numen 的战斗核：**顶层一个纯函数判据，执行层两条正交的腿**。规则在 `PetCombat`（不碰实体，可单测），执行在 `CombatMoveBehavior`（脚）与 `MeleeAttackWithAnim` / `HurtRangedAttackTargetTask`（手）。

**站位是一个带，不是两个状态。**内沿是「再近就不该站在这儿」，外沿是「再远就打不着」，带内站定挥刀。写成「太近→拉开、太远→靠近」两个状态的话，触发线和终止线是同一条，宠物会在线上来回抽。

| 情况 | 内沿 | 外沿 |
| --- | --- | --- |
| 剑 | 0 | `meleeFar`（两边碰撞箱 + 原版 `DEFAULT_ATTACK_REACH`） |
| 弓 | 5 | 15 |
| 爬行者（未点火） | 4（`FUSE_RADIUS`） | 无（剑）/ 15（弓） |
| 爬行者（引信在走） | 6（`BLAST_SPAN`） | 同上 |
| 脱离（血低） | 16 | 无 |

**爬行者对宠物而言永远不是一场能打的仗。**Numen 里未点火的爬行者算普通怪——因为玩家够得着 3.3 格、它 3 格才点火，中间有一格宽的窗口。宠物的够到距离只有一格半，窗口是负的，所以持剑的宠物对爬行者只有一个选择：离远点。弓手可以在爆炸范围外射。

**手和脚分开跑。**后退的宠物照样挥刀（两个行为同时在活动里），否则就是「躲的时候一刀不还，一路被砍到家」。弓手活动里也挂了近战行为：被贴脸且退不开时总得有个回答。

**脱离两条线**：血量降到 35% 脱离，回到 60% 才回去打。一条线会让宠物在线上进一下出一下。「已经脱离」是整场战斗里唯一需要跨 tick 记住的东西，就放在行为实例上（每只宠物一份）。脱离时优先往主人跑，但主人要比它自己离威胁更远至少 3 格——否则「退到主人身边」就是退到怪旁边。

**跑去哪里是算出来的，不是滚出来的。**随机选点必须承诺，否则宠物每 tick 换一个主意，就站在挖挖的引信旁边原地抖（实测过）；「直接背对它跑」下一 tick 还是同一个答案，不需要承诺。

**目标选择：**最近的，但**选中了就打完再换**（`PetCombat.pick`）。每次扫描重选最近的话，怪群里的宠物永远在转向。没有值得打的、只剩爬行者时，爬行者仍然是目标——「要离它远点」也得有个对象才能表达。

**传感器（`PetAttackbleEntitySensor`）三件事变了：**
- 扫描间隔 60 → 10 tick。三秒一次意味着僵尸能在宠物转头之前把主人砍四下。
- **主人的事算宠物的事**：打了主人的、盯上主人的、主人正在打的，都进候选。
- 选目标走 `PetCombat.pick`，不再自己写一遍「最近的」。

**许可表改了一行：**`COMBAT` 从「只有野生或自由活动」改成「除了坐下都行」。跟随中的宠物看着主人被打而不动手，是这套战斗「弱」得最明显的一处。

**出手节奉跟武器走：**宠物加了 `ATTACK_SPEED` 属性（基础 4.0，和玩家一样），所以铁剑的 -2.4 落得下去；冷却 = 20 / 攻速，夹在 [10, 20] tick。八个角色的属性构建合并成 `AbstractPet.petAttributes()` 一处。

## 6. 传感器

- **原则：** 传感器只采集信息，不判断约束、归属和职业；按目标种类写入各自的记忆，由意图决定用不用。
- **现有传感器调整：**
  - `PetFarmerWorkSensor`：去掉模式判断，分别写入 `HARVEST_POS`、`PLANT_POS`、`CONTAINER_POS`、`WEED_POS`、`MUSHROOM_POS`，不分昼夜和归属。野生宠物不收割作物，是因为许可表不允许野生宠物的 `WORK` 类别；夜里才采蘑菇，是 `pick_mushroom` 的前置条件。都不在传感器里判断。野草和蘑菇用方块标签 `entity_weeds`（矮草、高草、蕨、大型蕨）和 `entity_mushrooms`（红、棕蘑菇）。
  - `PetAttackbleEntitySensor`：去掉模式判断，保留目标合法性过滤和受击反击。
  - `PetPickableItemSensor`：去掉模式和驯服判断。
- **避免空转：** 传感器在当前能力用不上它的结果时跳过扫描，例如非农夫不扫描作物。这是性能判断，结果不影响行为。
- **遗忘远目标：** 农夫传感器忘掉离宠物超过 10 格的目标。意图只用 `reach` 内的目标，而传感器有目标时不会再扫描，不忘掉的话宠物会卡在一个用不上的目标上。
- **第一阶段的已知差异：** 跟随或坐下时，剑士和弓手的传感器也会记住附近的敌人，切到自由活动后会立刻开打。
- **新增传感器：** `PetBoardSensor` 每 40 tick 通过原版 `PoiManager` 查找 48 格内最近的公告板，写入记忆 `NEAREST_BOARD`；够不够得着由 `take_task` 按锚点判断。商店在第 9 步用同样的方式加。
- **POI 类型：** 公告板和商店注册为 POI 类型，查询开销和村民找工作方块相同。

## 7. 工作牌

代码在 `task` 包里：牌型、工作牌、公告板规则和到账都在这里，公告板方块在 `block` 包。

### 7.1 牌型数据

路径 `data/chiikawa/pet_task/<id>.json`，由 datagen（`PetTaskTypeData`）生成，`PetTaskTypeLoader` 加载：

```json
{
  "capability": "chiikawa:farmer",
  "counter": "chiikawa:weed",
  "amount": { "type": "minecraft:uniform", "min_inclusive": 8, "max_inclusive": 16 },
  "reward": "chiikawa:pet_task/weeding",
  "weight": 3
}
```

- `capability` 为能力的注册 id，`counter` 为工作计数（7.3），`amount` 是原版整数提供器，`reward` 为战利品表，`weight` 是公告板抽到它的权重。
- 能力或工作计数不存在时加载会打警告；解析失败的文件跳过。
- 不设"时间"字段：夜里才采蘑菇由 `pick_mushroom` 意图的前置条件决定，不在牌上再写一遍。
- 已有牌型：除草（农夫，8–16 株，权重 5）、街头演奏（乐手，120–240 秒，权重 1），讨伐随公告板升级加入（第 10 步）。**没有采蘑菇牌**：蘑菇只在夜里有得采，一张白天干不了的牌把农夫摔在那里等天黑。
- 报酬以绿宝石为主，30% 概率附带面包、蘑菇煲或曲奇。

### 7.2 工作牌

```java
public record PetTask(ResourceLocation type, ResourceLocation capability, ResourceLocation counter,
                      int target, ResourceKey<LootTable> reward, int progress) {}
```

- 同一个记录既是公告板上的牌，也是宠物身上的牌。牌自带计数、目标和报酬，数据包重载不会让已领的牌失效。
- 宠物身上存在同步数据里（存档键 `Task`），客户端据此渲染挂在肩上的小木牌、在背包界面显示进度。当前意图也同步一份，供背包界面显示"正在做什么"。
- 宠物死亡时在 `die` 里清掉，玩偶里不带失败的牌，复活也就不带。

### 7.3 工作计数与到账

`PetWorkCounters` 定义工作计数：`chiikawa:weed`、`chiikawa:pick_mushroom`、`chiikawa:play_music_second`；讨伐的 `kill_hostile` 随讨伐牌加入。

| 工作计数 | 在哪里上报 |
| --- | --- |
| `chiikawa:weed` | `CollectBlockBehavior` 拔掉一株草后 |
| `chiikawa:pick_mushroom` | `CollectBlockBehavior` 采下一朵蘑菇后 |
| `chiikawa:play_music_second` | `PlayMusicBehavior` 演奏中每秒一次 |

`TaskTracker.advance(pet, counter, amount)`：

1. 计数与身上牌的 `counter` 一致时累加进度。
2. 做满时按战利品表生成报酬放进背包，放不下的掉在脚下。
3. 冒出开心村民的绿色闪光粒子，触发 `PetReaction.HAPPY` 和开心语音。
4. 清掉牌并请求重评，当天还有对口的牌就会再去领。

带着街头演奏牌的乐手会反复演奏选好的曲子，直到牌做满。

### 7.4 公告板

`LaborBoardBlock` 是可合成的朝向方块（纸、木板、木棍），`LaborBoardBlockEntity` 保存当天的日序号和牌位列表，每个牌位是一张牌、预约（宠物 UUID、过期时间）和是否已被领走。规则在纯逻辑类 `BoardSlips` 里：

- **每日刷新：** 不在 tick 里刷新；当天第一次被查看时生成 3 张牌。种子由世界种子、日序号和方块坐标组合而成，同一块板同一天所有人看到的一样。
- **找牌：** 先找这只宠物自己预约着的；否则找第一张对口、没被领走、没被别的宠物预约的。
- **野生靠后：** 野生宠物要到日出后 12000 tick 才会去领，只领有主人的宠物剩下的。
- **预约：** 出发时占住一张牌，1200 tick 后自动失效，其他宠物不会奔向同一张。
- **领取：** 走到离公告板 3 格内时领走，牌从板上消失。
- **没领到：** 放掉预约，歇 600 tick（4.10）。
- **领走的记下来：** 牌位记下领走它的宠物名和主人名，界面据此显示。

**界面：** 右键公告板，服务端把当天的牌发给这名玩家（`BoardPayloads`），客户端打开 `LaborBoardScreen`：每张牌显示牌型、目标数量、给哪个职业，以及"还没人领"或"谁领走了"。界面只读，牌由宠物自己去领。

**长什么样、怎么画**：公告板是一块带人字小屋檐的木板，两根木柱、上下两根横梁，板上一排五个挂钩，当天的每张工作牌是挂在钩上的一块竖着的小木牌，写着几笔字，下面还贴着一张盖了红印的告示。模型是基岩版的（`models/entity/labor_board.json`，和挎包一样是一个「道具」，由 `PropRenderer` 画），每块木牌是一根骨骼 `Slip0`–`Slip4`。

方块本身不画东西（`RenderShape.ENTITYBLOCK_ANIMATED`，方块模型只留破坏时的粒子贴图），由 `LaborBoardRenderer` 按朝向把模型画出来，**只挂还没被领走的牌**：宠物领走一张，那块牌就从钩子上消失，远远就看得出今天还剩几张活。服务端每当牌位变动（领走、放回、换天、升级后补牌）就重算 `BoardSlips.hanging` 并推给附近的玩家——发出去的只有这一个数，谁领了什么、谁预约了什么都不出服务端。预约中的牌还挂着：宠物只是正走过去。

物品栏里的公告板是同一个模型，按原版方块物品的 3/4 视角（`block/block` 的展示变换）立在格子里，五块牌都挂着。

第 10 步加公告板升级。

## 8. 商店与送礼

### 8.1 商店

- `ShopBlock` 是可合成的朝向方块（木板、箱子、绿宝石），**实心**——柜台是站在旁边的东西，能穿过去就成了从里面自助。方块模型由数据生成，用原版贴图拼。
- `ShopBlockEntity` 只存一件事：这家店照哪份价目表做生意（默认 `chiikawa:general`）。两家店的区别只在那个 id。
- 注册为 POI；`PetPlacesSensor` 一趟扫描同时记下最近的公告板和最近的商店——两者查法一样、都放得稀，分两个传感器是把同一批 POI 扫两遍。
- 价目表路径 `data/chiikawa/shop_catalog/<id>.json`：

```json
{
  "entries": [
    { "item": "minecraft:cookie", "buy": 1, "sell": 0, "tags": ["chiikawa:pet_likes/snacks"] },
    { "item": "minecraft:wheat", "buy": 0, "sell": 1 }
  ]
}
```

- 主人通过交易界面买卖；`buy` 为 0 表示不出售，`sell` 为 0 表示不收购。

### 8.2 宠物购物

**性格多了一项 `likes`**（加权物品表，跟 `wild_tools` 同一形状）：这种宠物会拿自己的钱买什么。没写 `likes` 的宠物什么都不买——商店是它想去才去的地方，不是一项活。具体偏好按玩法文档第 8 节：吉伊零食、小八做饭材料、乌萨奇什么都买、狮萨饮品、摩门加小东西、栖子馒头下酒菜、拉库甜食、古本屋书。

**选购是纯逻辑**（`ShopBasket`）：拿性格的 `likes` ∩ 价目表在售 ∩ 买得起，按权重抽一件。**先想要，再谈买不买得起**——不是进店买一件能负担得起的最贵的。钱包（`Wallet`）只认绿宝石，且要么付清要么一分不付。

`shop` 意图：

1. 传感器记下最近的商店；意图上下文每次重评时问一句「这家店有没有它想要又买得起的」（只读，不改世界）。
2. 走到商店（到 2 格内，柜台 3 格内成交——留一格余量，同送货那个教训）。
3. **到了柜台才决定买什么**：路上可能又领了钱或花了钱。先确认背包放得下，再扣钱——背包满的宠物带着钱回家，不会付了钱换不到东西。
4. 买完歇 600 tick，免得满荷包的宠物站在柜台前把店买空。

**评分 0.65**：高于干活（0.6）、低于领牌（0.7）。这两条线决定了循环的形状：板子上还有牌就先去干活，牌领完了就拿刚赚的钱去买点东西，口袋空了再回去干。

**许可表**：`SHOP` 类别跟 `WORK` 一样——有主人且自由活动才去。野生宠物没有工钱可花，跟随中的宠物是跟着主人出门而不是自己出门办事。

### 8.3 送礼

**买的时候就分好了给谁**：约三分之一的购买是买给主人的（且要有主人、手上还没拿着别的礼物）——偶尔带份礼物回来的是宠物，买什么都上交的是快递员。

礼物存在 `AbstractPet.pendingGift`，**不在背包里**：那是拿在手上的东西，不是行李。主人翻背包拿不走还没送出的礼物，宠物也不会把它花掉。

`gift_owner` 意图：走到主人身边，把礼物放进主人物品栏（满了就掉在脚下——因为背包满就拿着不给，等于没送），配心形粒子、开心反应和语音。

**评分 0.85**，高于宠物为自己做的任何事：送礼是唯一一件它希望被看见的事，隔了三个活才递过去的蛋糕已经不是同一块蛋糕。`GIFT` 类别只要不是「坐下」就允许：跟随中顺路递，自由活动中特地送回来。

**买给自己的那份**进背包；如果是食物且宠物带伤，就当场吃掉回血（回血量与主人喂一口共用同一常量）。买了蛋糕抱着、自己一瘩一拐，是对钱的用途有误解。

**在聊天框里说一声**：宠物花钱、送礼多半发生在主人看不见的地方，所以每买一样、每送一样都告诉主人（`AbstractPet.tellOwner`）：谁、花了几颗绿宝石、买了什么，并区分留着、当场吃掉、说要送你三种；送到时说送了什么。物品用原版聊天里的 `[名字]` 写法，悬停能看详情。整行是灰色斜体，像书里写人物动作那样，跟玩家说的话分开。只发给主人本人，而且主人得在宠物所在的世界里——隔着维度说一件看不见的事没有意义；野生宠物没有主人，不说。

### 8.4 主人给东西

`PetInteractHandler` 增加一条：**手持绿宝石右键 → 放进宠物背包**，触发开心反应并请求重评（它马上就能去买东西）。背包满时一分钱不收，不凭空消失。钱怎么花是宠物自己的事——这就是宠物和自动售货机的区别。

手持食物右键仍是喂食（回血）；宠物用品的交付等用品做出来再说（第 10 步）。

### 8.5 交易界面

右键商店 → 服务端把这家店的价目表发给这名玩家（`ShopPricesPayload`），客户端开 `ShopScreen`：每行是图标凹槽 + 名字 + 两个按钮。**价格写在按钮上**——按「买 3」就是花三块买下它，不在旁边再写一遍价钱。买不起 / 手上没货的按钮变灰；标题栏右侧是身上的绿宝石数。

成交走 `ShopTradePayload`，**报物品 id 而不是行号**：开屏到点击之间数据包重载会把行号抽掉。服务端重新校验距离、价目表、钱和货——界面只是服务端一瞬前的图片，柜台才是成交的地方。`ShopTrade` 保证整笔成交或完全不动：先做可能失败的那一步（放不下货 / 手上没货），再做不会失败的那一步。

## 9. 野生吉伊

- **生成：** 在 `finalizeSpawn` 中，自然生成和区块生成的野生宠物按性格的 `wild_tools` 抽取工具放进主手（背包第一格），设置 `PetDirective.FREE`。
- **驯服：** 重写 `tame`，驯服成功后设置为 `FOLLOW`，背包内容保持不变。
- **家的位置：** `AbstractPet.settleHome` 是唯一的家规则：自由活动以当前位置为 `HOME`，跟随清除 `HOME`，坐下保留。`setPetDirective`（交互切换、野生生成、驯服）和复活仪式都调用它，所以复活的自由活动宠物以蛋糕位置为新家。
- **死亡掉落：** `getEquipmentDropChance` 对所有槽位返回 0，工具和装备完整留在玩偶里，有主人和野生的宠物都一样。
- **时段：** MORNING 23000–3000，DAY 3000–12000，EVENING 12000–13000，NIGHT 13000–23000；没有昼夜循环的维度用它的固定时间，例如下界算夜晚。

## 10. 界面

界面全用代码画，不用贴图，风格一处说了算，所以加一块面板不用再画图。

### 10.1 设计原则

这几条是布局的依据，不是口号：

- **标签是最后手段。**「数量：12」把一行分成没用的一半和有用的一半；「12 株」自带含义。非配不可时，标签压暗、值留亮。
- **能用图形说的不用字。**牌型用图标，进度用条，状态用徽章——一眼就能分辨，不用逐行读。
- **文字下沉悬停。**行里只留区分彼此的那一样东西，其余（给哪个职业、谁领走的）放到鼠标下。列表是用来扫的，不是用来读的。
- **间距成组。**组内小、组间大，只用 `TIGHT/GAP/PAD/GAP_SECTION` 四档；随手填数字出来的是「差一点对齐」，那正是没排过版的样子。
- **深度而非粗边。**卡片用硬阴影浮起来，凹槽用比卡面暗的底色，都比加粗描边安静。
- **每块面板都是一张贴纸。**对标 Chiikawa 官方手游「ちいかわぽけっと」：1 像素深棕墨线、线内一圈白边、奶油色纸底，圆角是逐行算出来的曲线（`Ui.sticker`）。换掉了原来「米色 + 斜面」的原版语法——米色底上斜面几乎看不见，整个界面发糊。
- **颜色只给有活的东西。**粉色＝选中 / 主要；草绿＝工作与进度；天蓝＝宠物立绘的背景；木头＝写名字的牌子。其余都是纸和墨。
- **原作的母题。**名字写在挂在面板上沿的木牌上（公告板的材料），图标是自己画的小像素画（工作牌、对话气泡、爪印……）。

### 10.2 `:ui` 模块

`ui` 是个独立的 Gradle 子工程，只依赖 JDK，编译期看不到 Minecraft。两个 loader 像编译 `common` 那样把它的源码编进成品（`uiJava` 配置），所以成品里没有多出一个库。

- `DrawSurface`：整个模块跟游戏之间只有这五个调用——`fillRect`、`drawText`、`drawIcon`、`textWidth`、`lineHeight`。
- `Icon` 是个空接口：模块只给图标留位置，从不看里面是什么，游戏那边 `ItemIcon` 包一个 `ItemStack`。这是「排满物品的界面」和「纯 JVM 模块」能共存的原因。
- `UiTheme` 是一张语义色表（纸 `PANEL`、墨 `INK`、白边 `HIGHLIGHT`、浅槽 `SURFACE`/`SHADE`、粉 `ACCENT`/`ACCENT_SOFT`/`ACCENT_PALE`、绿 `LEAF`/`LEAF_PALE`/`SUCCESS`、天蓝 `SKY_PALE`、木 `WOOD`/`WOOD_LIGHT`/`WOOD_DARK`），部件只报槽位不报颜色；`UiStyle` 是间距与尺寸，并带 `centerIn` 这类对齐助手。两者都写了收录纪律：只收多个界面共用且承载设计意图的值。
- `Ui` 管底板：`roundRect`（逐行算曲线的圆角框）、`sticker`（墨线 + 白边 + 填充）、`panel`、`card`（带阴影）、`well`（浅槽）、`divider`（虚线）、`rowHighlight`、`textRight`、`textCentered`、`textClipped`、`emptyState`。`PixelArt` 是字母格子画的小图标。
- `ui.widget` 管卡面上的东西：`Slot`、`Bar`、`Badge`、`Chip`、`Tooltip`、`Hearts`（粉色墨线心）、`Arrow`、`Sign`（挂着的木牌）、`Tabs`（面板上沿的标签，选中的和面板连成一片）、`TitledPanel`（挂牌的面板）。
- 模块自己有单元测试，用假的 `DrawSurface` 记下画了哪些矩形、字和图标，断言的是**最终显示出来的像素颜色**（`colorAt`）——圆角是很多矩形叠出来的，测「画了哪几个矩形」没意义。`PreviewTest` 还会把所有部件画到 `ui/build/ui-preview.png`，不起游戏就能看到实际几何。比如「才做一点的条不能四舍五入成空」「快完的条不能画成满」这种规则，都是测试监着的。

游戏这边都在 `client.ui.mc`：`GuiSurface` 包 `GuiGraphics`，给各个 Screen 用，并提供 `onTop` 把悬停卡画在 z=400（不然物品图标会从卡里穿出来）；`WorldSurface` 包 `PoseStack` 和 `MultiBufferSource`，把同样的部件画到世界里；`UiButton` 继承原版 `AbstractButton`，只接管绘制——点击、键盘、焦点、旁白都还是游戏的。

**贴图已全部退出界面**：`assets/chiikawa/textures/` 下只剩 `entities/` 和 `item/`——那些是画，不是界面。

### 10.3 牌型的图标

牌型 JSON 多了一个 `icon`（物品 id），滚出牌子时连同 capability、counter、reward 一起拷进 `PetTask`。牌子本来就是「自带全部信息」的设计（§7.2），图标跟着走才有两个好处：客戶端不需要拿到数据包就能画头顶标签（牌型只在服务端加载），公告板包也只多了一个字段。老存档里没图标的牌子显示空格子，不报错。

### 10.4 公告板界面

标题栏右侧是今天几张牌。每行：左边图标凹槽，接着牌型名，紧跟一个压暗的「限农夫」，右边数量（压暗）和一枚状态徽章（待领 / 已领）。鼠标移上去整行变色，并弹出悬停卡：牌型名、限哪个职业、要多少、谁领走了。

「限谁领」不能下沉到悬停卡：主人看板子第一件事是判断「我家有没有宠物接得了这活」，那是主问题不是细节。宽度不够时先截牌型名，职业保持完整——名字截了还能猜，职业截了这一行就不回答问题了。只有「谁领走的」留在悬停卡里，因为宠物名字长度不可控。

### 10.5 头顶标签

**准星指着、且够得着才显示**：直接用游戏自己的 `entityRenderDispatcher.crosshairPickEntity`——它按玩家交互距离（`Attributes.ENTITY_INTERACTION_RANGE`，生存 3 格、创造 5 格）算出「此刻准星指着的实体」。能伸手摸到它，才问得出话；这条规则连数字都不用我们定，也跟原版给命名生物显示名牌的条件一致（`MobRenderer.shouldShowName`）。

不自己投长射线：那就又多一个「多远算数」的拍脑袋数字，而「能不能互动」是现成的、玩家已经熟悉的界线。

不常驻是故意的：十几只宠物同时顶着牌子，那不是信息是噪音；问一只答一只，准星就是那一问。

**不做淡入淡出**：准星落上去那一帧出现，移开那一帧消失，跟原版名牌一样。Minecraft 里的东西都是这么出现和消失的，只有这块牌子渐隐渐现，反而显得不合群。闲着且没牌的宠物指了也不说话（`PetStatusText.chip`），别人的宠物不显示，按 F1 跟 HUD 一起隐藏。

小卡是 `Chip`：左边牌型图标，中间在做什么，右边一根进度条。**不写数字**：路过一眼、距离不定的标签能承载图和长度，承载不了除法；要看「7/11」就开背包，那里有地方写。

画法：朝向摄像机、缩到文字像素的面上，填充走 `RenderType.textBackground()`，文字走 `Font.DisplayMode.NORMAL`，两者都测深度，所以隔着墙看不见。不能用原版名牌那套底色：它画在自己字形的前面，只有 see-through 模式才正常，而 see-through 正是隔墙可见。

屏幕上没有深度，后画的自然盖住先画的；世界里所有东西都落在同一个平面上，而**同一平面上的两块填充会打架**——面板的边框和里面的底色深度只差最后一位浮点，出来就是一行边框一行底色的横条。所以 `WorldSurface` 每调用一次就把 z 往摄像机方向挪 0.1 个文字像素，部件要的「后画的盖住先画的」这条就成立了，不靠深度运气。每个标签新建一个 `WorldSurface`，层数从头数，标签不会越飘越远。世界里画物品图标时额外向前推半个图标的深度，否则方块模型的后半截会埋进卡面里。

宠物拿着工作牌时，肩上挂一块小木牌（`SlipTagLayer`，挂在胸前实体坐标 y 4.5、z -4.8），远看就知道它在打工。

**界面里的立绘不画标签**，也不画原版名牌：打开宠物界面时准星正指着它，按上面的规则它「被问到了」，立绘会顶着一块牌子。标签是世界在回答主人的指点；进了它自己的界面，该说的界面都说了。宠物界面把立绘包在 `ChiikawaEntityRenderer.drawPortrait` 里画，这一段里 `shouldShowName` 一律为假。

### 10.6 宠物界面（三个 tab）

面板上沿三个图标 tab，名字挂在右上的木牌上，血量在木牌下。**面板高度跟着当前页的内容走，顶边不动**（按最高的背包页居中一次），切页时 tab 和名字不跳。

- **背包**（双肩包图标）：立绘、手上工具和包格、口袋、包的十格（没背包时是虚线框 +「+10」，说明在悬停里）、立绘下的工作牌小条、玩家背包。格子间距 18，布局仍由菜单定，屏幕问每个格子在哪。
- **状态**（工作牌图标）：工作牌卡片（名字、正在做什么、进度）、干劲和零花钱两个小胶囊（悬停看说明）、准备送你的礼物、职业。这些以前根本没地方显示。
- **指令**（对话气泡图标）：跟随 / 坐下 / 自由活动三张大卡，当前的粉色打勾，点一下就换。走 `PetDirectivePayload`，服务端 `PetServerPacketHandler.order` 检查是不是主人、离得够不够近（和菜单同一个 8 格）。蹲下右键循环仍然保留。

**非背包页所有格子都关着**（`PetBackpackMenu.showSlots`，只在客户端关），玩家自己的也是——看不见的格子不该能扔东西进去。服务端永远全开，所以服务端的行为不依赖主人在看哪一页。

**为此同步了两样数据**，都是一个来源：礼物（`GIFT`，原来是服务端字段）；干劲从「剩多少 tick」改成「到哪个游戏时间结束」（`EAGER_UNTIL`）——倒计时每 tick 都变，同步就是每 tick 一个包；结束时间只在喂的时候发一次，客户端自己算还剩多少。

公告板、商店、八音盒换成 `TitledPanel`：名字挂在左上的木牌上，其余跟着主题自动变。效果图在 `docs/ui-mockups/`。

### 10.7 音乐盒界面

同样整屏代码画，`music_box.png` 已删。标题栏右侧是页码；每行一首曲子，鼠标移上去整行变色；导入中 / 失败的曲子**留在列表里带一枚徽章**，而不是消失——玩家刚放进去又找不到的文件，比一个写着出错的行更难受。

底部一排控件：两侧翻页箭头（`Arrow`，三角形用像素画，不需要翻译），中间「打开文件夹」「刷新」两个文字按钮——这两个动作用 8 像素的图标说不清楚，写出来反而直接。按钮是 `UiButton`：继承原版 `AbstractButton`，只接管画法。


### 10.8 手持物品

`HeldItemLayer` 把主手的东西画在模型的 `RightHandLocator` 上。**先转进拳头，再交给原版**：物品的第三人称展示变换是按原版的手写的——原版 `ItemInHandLayer` 从手臂出发先绕 X 转 -90°、绕 Y 转 180°，让物品的「上」从拳头前方伸出去；车万女仆对手部定位骨骼也是同一步，再往前挪 2 像素、往下 1 像素。我们的模型空间是原版模型空间经 `scale(-1, -1, 1)`（即绕 Z 半圈）翻过来的，两者合起来正好是一次绕 X -90°（`HeldItemLayer.intoFist`）。

少了这一步时，剑柄朝下、剑身直指天空，并且从拳头根部穿过脑袋；手臂一挥，剑身往身后甩——看起来像挥反了。

**再抬一点、缩一点**：原版人形一拿东西就把手臂往前抬十分之一圈（`ArmPose.ITEM`，18°），工具才朝前上方指；宠物的动画里没有这一抬，就由手来抬。宠物大约只有玩家一半高，按玩家的尺寸拿，一把剑跟宠物一样长、还戳进身前的地里，所以手里的东西缩到 0.6——原版给它自己的小个子悦灵也这么缩。两个数都在 `HeldItemLayer` 一处。

`HeldItemLayerTest` 把方向钉住：物品的「上」指向前方略偏上、正面朝天、侧面不翻，握点在往前 2 像素、往下 1 像素处，并且比玩家手里的小。

**武器怎么握，写在武器模型里**：吉伊、小八、乌萨奇的三把武器是竖着建的长杆，第三人称展示原先是空的（或旋转为 0），按原版手势会像长枪一样横在身前、从中段握住。现在三者的 `thirdperson_righthand` 都是绕 X 转 45°、沿杆身推 5 像素、缩放 0.85，加上拿东西时手臂那 18°，合起来约 63°：握在杆尾附近，斜着往前上方举。宠物和玩家拿它们都读这一处，不另设宠物专用的角度。

## 11. 宠物用品

### 11.1 双肩包与挎包

戴上后背包多出 10 格，并显示在宠物身上。四个包，两种背法：

- **双肩包**（`backpack`）：动画里大家出门干活、去讨伐都背的那个灰色圆包，背在后背，两条肩带。原作里人人都背，所以它是所有宠物的通用款。
- **挎包**：吉伊卡哇的粉色小熊（`bear_pouch`）、小八的蓝色鲸鱼（`whale_pouch`）、乌萨奇的黄色星星（`star_pouch`），挂在腰侧，一条白色斜挎带。官方周边只有这三款。

哪只宠物背哪个由主人定：任何宠物都能背任何一个，功能完全一样，差别只在样子。

**「是不是包」只问一处**：`BagItem`。宠物、背包格、渲染层、带子的显隐都问 `BagItem.isBag`；背法是 `BagItem.Wear`（`SLUNG` 斜挎 / `ON_BACK` 背在后背），每种背法对应宠物模型里的两根骨骼。

**模型：包只有一份，挂点和带子长在宠物身上。**

- 每个包是一个基岩版模型（`models/entity/<物品 id>.json` + `textures/entities/<物品 id>.png`），一根骨骼、以原点为中心、正面朝 -Z。物品栏、手上、地上、展示框、背在身上，都是这一份。
- 每只宠物的模型里有四根骨骼，都挂在 `Body` 下，跟着身体一起动：`PouchLocator` / `PackLocator` 是空的挂点，位置和朝向在 Blockbench 里贴着这只宠物的身体摆好；`PouchStrap` / `PackStrap` 是带子本身，画在宠物自己的贴图上（贴图空白处各有一块 4×4 的带子花纹，白色一块、灰色一块）。
- 渲染：`BagLayer` 按背法找到挂点，用 `PropRenderer` 把包的模型画在那里；带子由宠物渲染器基类里每种背法一条显隐规则控制，背着这种背法的包才显示——和小八的吉他是同一套机制。
- 风狮爷的尾巴比包长，会从双肩包正面戳出来，所以它的渲染器多一条规则：背着双肩包时收起尾巴。其他宠物的尾巴都被包盖住。

**物品形态**：物品模型只有 `{"parent": "builtin/entity", "gui_light": "front"}`（common 的 `PropItemModelProvider` 生成，两个 loader 共用），由内置物品渲染器（NeoForge 的 `IClientItemExtensions`、Fabric 的 `BuiltinItemRendererRegistry`）交给 `PropRenderer.drawItem`。它借用原版 `item/generated` 的展示变换，把包的正面转到精灵图正面的方向，并按模型实际大小缩放到和精灵图一样占满格子——所以包在手上、地上、展示框里的摆法和任何平面物品一致，只是它是立体的。

**美术怎么做的**：每个包先在像素格上画正面轮廓（熊脸、鲸鱼、星星、带盖的圆包），按行切成方块拼出圆润的外形；轮廓每往里缩一圈就再叠一层，挎包前后都鼓（毛绒感），双肩包背面贴平、只往外鼓。每行方块的正面按它在轮廓图里的位置取贴图，所以五官和缝线在立体上也对得齐。在 Blockbench 里搭好、挂到每只宠物身上看过再导出，导出的 JSON 就是资源本身。

**约定由测试守着**（`PropModelsTest`）：有动画的模型（宠物）必须带齐两种背法的挂点和带子，挂点是空的，带子和挂点在同一根骨骼下；没有动画的模型（道具）必须是代码会画的——包或公告板——并且有贴图；包只有一根骨骼、以原点为中心。

**包存在背包容器的固定格位里**，跟主手同一个套路：`getItemBySlot(MAINHAND)` 读第 0 格，`getItemBySlot(CHEST)` 读第 1 格。好处是它自动跟着背包存档、跟着玩偶回来，不用另写一套装备同步。

容器总大小 27：0 主手、1 包、2–16 基础格（15 格，界面里正好三排、每排五格），17–26 是包的格子。后十格的 `Slot.isActive` 看宠物有没有背包——没背时界面那一块画成提示行而不是空凹槽（空凹槽是「这里可以放东西」，提示行是「背上包就能放」）。直接拿另一个包换下身上的包，宠物一直背着包，那十格里的东西跟着进新包。

**摘包时里面的东西掉在脚下**，不凭空消失也不偷偷塞回基础格——这是玩家能预期的唯一行为。

**旧存档迁移**：以前第 1 格是普通存储。读档时如果第 1 格里不是包，就把它挪到第一个空基础格。

### 11.2 简单料理

喂给自己的宠物，接下来 6000 tick（四分之一天）干活更起劲。面包 + 磗 + 任意作物合成，商店也卖，3 维度一份。

**「干活更快」落在两处**：移动速度一枚不存档的 `ADD_MULTIPLIED_BASE` 修饰符（`chiikawa:eager`，+30%）；意图打分给 WORK / FORAGE 加 `EAGER_BONUS = 0.15`。干活本身是一瞬的事（能够到就拔草），所以「更快」只能是早点走到 + 少磨蹭一点。

**0.15 小于接单的 `TASK_BONUS = 0.2`**：一顿饭只是让宠物更想干活，赢得过闲逛，赢不过手里的单子，更越不过主人的指令——吃饭不会把宠物变成另一只宠物。

**再喂一份是续时间而不是叠加**（`max` 而非 `+=`，修饰符永远只挂一枚）——否则手里有料理就能让宠物永久疾跑。计时在 `customServerAiStep` 里递减，存 `Eager`，读档后重新挂回修饰符。

### 11.3 名字牌

用原版名牌，不自己做一个——玩家已经知道怎么用，只需要把它上架到商店。

### 11.4 公告板升级

主人花绿宝石给公告板升级：Lv.1 → 16 颗 → Lv.2 → 32 颗 → Lv.3。每升一级每天多一张牌（3 / 4 / 5），并解锁更难的活。

**牌型多了一个 `min_level`**（可选，默认 1）。讨伐牌（`melee_hunting` 剑士 / `ranged_hunting` 弓手，计数器 `slay`）写 2，所以升级买的不只是「更多同样的活」，而是新活。讨伐报酬最高（4–7 颗），也是唯一会失败的活——宠物倒下时 `die` 先清牌，玩偶不会带着牌回来。

**计杀只接一处**：`AbstractPet.awardKillScore`。原版把击杀功劳给造成伤害的那个实体（箭也算射手的），所以剑与弓在同一个入口汇报，只数 `Enemy`。

**升级不重滚今天的牌。**每张牌用 `seed + index * 质数` 各自滚，所以 `topUp` 只补缺的那几张，已经贴在板上、已经被领走的那几张原样不动——中午付的钱不该把别人宠物正在干的活抹掉。等级存在方块实体的 `Level` 键（字段叫 `boardLevel`，因为 `BlockEntity.level` 已经是世界）。

**界面：**公告板屏底部一条分割线，左边 `Lv.N` 徽章 + 「每天 N 张」，右边一个写着价钱的升级按钮（钱不够时变灰），鼠标移上去才说升级给什么、你身上有多少——细节下沉 tooltip。

**服务端再检一遍**：`BoardServerPacketHandler.buyLevel` 检距离、检等级、整数付清（`Wallet.pay`）；`handleUpgrade` 只是它加一句「把板子现在的样子发回去」，买成买不成都发，玩家看得到为什么。这也是为什么判断单独一个方法：GameTest 里的假玩家没有真连接，NeoForge 不允许向它发自定义包。

### 11.5 跟随不丢宠物

**问题：**宠物只在自己思考的时候才会发现主人走远了。处在「只加载、不运算」区块（别的玩家视距边缘、出生点区块边界、区块加载器的圈）的宠物根本不思考，也就永远不会把自己传送回来。这是 0.0.9 就发现、留到这一版的缺口。

**做法：把传送收成一个来源，放在服务器侧。**`PetFollowKeeper.tickServer` 每 40 tick（2 秒）扫一遍有玩家的维度，把落下太远的跟随宠物传到主人身边。判断用的还是同一个 `PetAnchor.beyondTeleport`，所以坐着、被拴、骑乘、自由活动、野生的宠物都不会被拖走。

- `AnchorLeashBehavior` 只剩「走回去」，不再传送——否则同一件事两个地方写，谁先生效看运气。
- `PetUnloadFollow`（区块卸载前的 mixin）留作兼顶：两次检查之间区块真的卸了，宠物就不在内存里了，扫也扫不到。
- 主人在别的维度时不动：普通传送跨不了维度，那是召回道具的事。

### 11.6 宠物铃铛（召回）

**右键一响，你名下的宠物都回来**——同维度的、未加载区块里的、别的维度的都算。代价是冷却 600 tick（30 秒），不消耗：找回丢了的宠物是补救，不该收钱；但一秒能敲十下的铃就不是找宠物，是随时把宠物拽来拽去。

**`PetRoster`（存档数据）：**每只宠物最后被看见的地方（主人、名字、维度、坐标），存在主世界的 `DataStorage` 里，整个服务器一份。写入时机三处：驯服时、每 100 tick、以及**区块卸载前的那一下**（`PetUnloadFollow.onChunkPreUnload`，原本就有的 mixin 钩子）——最后这一处才是重点，因为之后发生的事情都是在宠物已经不在世界里的情况下发生的。跨维度时也记（`changeDimension`）。

**铃响之后不是立刻结束的。**已加载的宠物当场就拉回来；剩下的要先把它们那块区块叫起来，而**区块加载完不等于实体已经读回来**（实体是接下来几 tick 里陆续读的）。所以 `PetRecall` 把一次铃声当作一件持续 60 tick 的事：每 tick 再看一眼，谁出现了就拉过来，到点才给主人一句话。这也是为什么报告写在 `PetRecall` 而不是道具里。

- 一次最多叫醒 16 块区块，剩下的直接列在「没有应声」里——一口气加一百块区块的铃是卡服务器的铃。
- 叫不到的宠物从名册里删掉：它可能已经用玩偶复活成了另一只，或者被别的东西从世界里拿走了。说一次，不年年说。
- 坐着的宠物也会回来，并且回来之后还是坐着：叫它是主人开口，而「待在那里」的回答不是「那你就待着」。

**合成：**金锭×3 + 绿宝石 + 木棍；商店 16 颗。图标是占位的手画 16×16。

### 14.1 GameTest

单测能证明「挑牌的规则对不对」，证明不了「宠物到底会不会干活」。后者得在真世界里跑：

```
./gradlew gameTest      # 无头跑全部用例，退出码 = 失败数（转 :neoforge:runGameTestServer）
```

**用例为什么在 NeoForge 而不在 common：**原版把模板 id 定成 `<类名小写>.<template>`、命名空间默认 `minecraft`；NeoForge 靠 `@GameTestHolder("chiikawa")` 改命名空间，而那是 NeoForge 专有注解，common 里写不了——没有它，用例会被 `enabledGameTestNamespaces` 过滤掉。宠物逻辑几乎全在 common，跑一个 loader 照样测得到；Fabric 侧的平台服务、网络、注册由双 loader 的 RCON 冒烟覆盖。

**地板由数据生成：**`GameTestStructureProvider` 写出 `chiikawa:floor16` / `chiikawa:floor8` 到 `data/chiikawa/structure/`。不用仓库里的 SNBT 目录加系统属性指路：游戏找模板先问自己的结构管理器，数据包是两个 loader 都认的那一处。模板落位在测试原点 +1，所以地面在 rel y=1、站人在 y=2。

**共用件 `GameTestKit`：**每个批次自己定住难度、时刻、天气、关掉自然刷怪——批次顺序不由人定，继承上一批的和平难度会把战斗用例变成空转。另有生成野生 / 有主人宠物、塞工具、数背包的助手。

**目前没盖到的：**演奏家真的演奏——需要一首可播放的曲子，而曲库来自玩家自己的音乐文件夹；要测得先造一个测试专用的音轨。存档跨重启的保持（牌子、家的位置）也不在游戏内用例里，那是单测的活。

**写用例踩过的两个坑，都是用例自己的错：**

1. 战斗批次本来定在正午，僵尸在太阳底下自燃掉血——三条用例里有两条是靠晒死过的假阳性。改到半夜。
2. 公告板一天滚 3 张，除草和采蘑菇**都是农夫的活**。只保证「今天有除草」不够：先撞上采蘑菇的话，大中午没蘑菇可采，永远领不到钱。改成按宠物真正的挑牌规则（第一张农夫牌）找板子位置。

用例不往方块实体里塞牌子，而是拿同一个 `BoardSlips.roll` 逐个位置算过去，选中今天确实先给农夫除草的那一格——否则测的就是一块玩家永远遇不到的板子。

**干活类用例用勤快的西萨（`GameTestKit.worker`）：**性格会把「溜达」和「干活」放在一起称，乌萨奇的 `WANDER` 权重是 2.0——拿它测「活干没干成」，测的是今天它想不想干。懒宠物的行为值得单写一条用例，不该混在每条里掷硬币。

**职业不只看工具，还看物种：**演奏家只能是八字（`MusicianJob.canAssume`）。写用例时我先写错了——以为拿了音乐盒就是演奏家。现在两面都锁住：乌萨奇拿音乐盒仍是无职业，八字拿音乐盒才是演奏家。这种规则最容易在重构里被惄惄抹掉。

**用例押出来的真 bug（都已修）：**

【一】**讨伐牌的计数原本跟着原版的「击杀功劳」走。**原版把功劳优先记给最后打过它的玩家，所以主人只要砍过一下，宠物补的那一刀就不算它的了——而「和自家宠物一起打」正是最常见的打法。旧用例只让宠物碰过僵尸，恰好绕开了。现在按**致命一击是谁打的**算（读伤害来源，箭算射手的），写在 `LivingEntity.die` 的 mixin 里一处。

【二】**挥刀的门槛挂在一个每 20 tick 才刷新的记忆上**（`NEAREST_VISIBLE_LIVING_ENTITIES`）。刚锁定目标、或刚动起来的宠物因此最多有一秒挥不出刀；「边退边还手」那条用例把它拽了出来。改成直接问世界要视线（`hasLineOfSight`），每 tick 都是真的。

【三】送货时宠物走到「离箱子 3 格」就停，而放东西的判定是「距离平方 ≤ 9」——箱子中心比脚高半格，平方就是 9.25，恰好越界。宠物会站在箱子旁边抱着菜不动，成不成全看寻路停在哪。仓库里本来就有正确写法：领工作牌是「走到 2 格内、3 格内才领」，留了一格余量。送货改成同样的余量。
